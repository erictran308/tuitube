# Build tuitube accountless around yt-dlp and mpv

As of October 2026, the best and most secure way to build tuitube is an accountless-by-default, MIT-licensed Rust TUI that contains none of YouTube's cipher or InnerTube code itself. Subscriptions live in local SQLite (imported once from Google Takeout, refreshed from public channel RSS), a version-pinned, config-free yt-dlp subprocess with Deno handles search, channels, comments and stream resolution, and a spawned mpv, started with `--no-config` and driven over a private socketpair JSON IPC channel, plays the URLs tuitube resolved. The official Data API is the only route Google sanctions, but it cannot play a video in a terminal and has returned nothing for Watch Later, history or the home feed since 2016, so it belongs only in an optional OAuth mode (the user's own Cloud project, `youtube.readonly`) for importing subscriptions and playlists. Every unofficial route breaches YouTube's Terms of Service, yet from 2023 to 2026 YouTube enforced against traffic rather than people (bot checks, PO tokens, SABR-only streams, IP blocks), this research found no confirmed account termination for light personal use, and the lawsuits targeted distributors of download tools, not users. The real stake is the Google account, so any login must be an explicit opt-in with a throwaway account and pasted cookies, never browser extraction. Maintenance decides the backend: all logged-out playback now depends on one app identity (VISIONOS), YouTube breaks extractors roughly six to eight times a year, yt-dlp usually ships a fix within one to three days, and the only native Rust library, rustypipe, is GPL-3.0 and has not had a release since April 2025. Most of the security work is about integration choices rather than exotic exploits: no shell, pinned binaries, config- and plugin-free invocations, a locked IPC channel, escape-scrubbing of every remote string, and a single gate on anything that tells YouTube what the user watched.

## Google's sanctioned route yields a metadata browser, not a player

A single-user desktop app can use the Data API v3 legally, and the setup options have narrowed. For macOS, Linux and Windows, Google recommends a "Desktop app" OAuth client with a loopback redirect and PKCE. It has dropped both custom URI schemes ("due to the risk of app impersonation") and the manual copy-paste flow, and it treats installed apps as unable to keep secrets ([Google](https://developers.google.com/identity/protocols/oauth2/native-app)). The device-code flow is attractive for SSH sessions, but it needs a separate "TVs and Limited Input devices" client and supports only `youtube` and `youtube.readonly` among the YouTube scopes ([Google](https://developers.google.com/identity/protocols/oauth2/limited-input-device)). Publishing status matters more than client type. A project left in **Testing** gets refresh tokens that **expire after 7 days**. Each OAuth client also keeps at most 100 refresh tokens per Google account and silently revokes the oldest when a 101st is minted, which repeated re-authentication during development will trigger ([Google](https://developers.google.com/identity/protocols/oauth2)). An app "for your personal use (fewer than 100 users)" can instead go **In production while unverified**. The user clicks through an "unverified app" warning at each consent and gets normal long-lived tokens ([Google Cloud Help](https://support.google.com/cloud/answer/13464323)). Full verification would demand a homepage on a verified domain, a privacy policy and a demo video ([Google Cloud Help](https://support.google.com/cloud/answer/13464321)), which is disproportionate for one person. The right official setup is therefore the user's own Cloud project, a Desktop client, loopback plus PKCE, `youtube.readonly` (adding `youtube` only if tuitube ever writes), and production-unverified status. Shipping one embedded client ID would put every user under the author's quota and the 100-user cap, and would make the author the "API Client" operator the Developer Policies regulate.

Quota no longer constrains a personal feed, but it does constrain search. Since **1 June 2026** the default allocation has been **10,000 units a day** for most endpoints, plus **separate 100-call daily buckets** for `search.list` and `videos.insert`. `subscriptions.list`, `playlistItems.list`, `videos.list` and `channels.list` cost 1 unit each. Writes such as `subscriptions.insert`, `playlistItems.insert` and `videos.rate` cost 50 ([YouTube Data API](https://developers.google.com/youtube/v3/determine_quota_cost); [revision history](https://developers.google.com/youtube/v3/revision_history)). A 300-channel feed built from each channel's uploads playlist costs roughly 310 units per full refresh: 6 for the subscription list, 300 for the playlists and a few for video details. That allows about 30 full refreshes a day, or one every 45 minutes. Search is the binding limit at 100 queries a day. Raising quota requires an API Compliance Audit that no hobby project will pass ([Developer Policies](https://developers.google.com/youtube/terms/developer-policies)).

The deeper problem is what the API cannot do. Watch history and Watch Later were deprecated in September 2016, and `playlistItems.list` on `HL` and `WL` has returned an empty list ever since. The `home` feed now returns what "a logged-out user sees", and no subscriptions-feed method has ever existed ([revision history](https://developers.google.com/youtube/v3/revision_history)). `captions.download` works only for videos the user has permission to edit ([YouTube Data API](https://developers.google.com/youtube/v3/docs/captions/download)). Above all, the API serves no streams. Its terms grant "no rights or licenses… to reproduce or distribute audiovisual content" ([API Services ToS](https://developers.google.com/youtube/terms/api-services-terms-of-service)). The Developer Policies (updated 14 September 2026) forbid caching AV content (III.E.1.a), separating audio from video (III.I.7), background playback (III.I.9), blocking ads (III.I.5), modifying the player (III.I.6) and using undocumented APIs (III.D.7) ([Developer Policies](https://developers.google.com/youtube/terms/developer-policies)). Sanctioned playback means the embedded player: at least 200×200 pixels, in an OS WebView, with no overlays ([Required Minimum Functionality](https://developers.google.com/youtube/terms/required-minimum-functionality)). A terminal cannot host that. An official-only tuitube would browse subscriptions, search 100 times a day, manage playlists and hand every video to a browser. It would also owe YouTube on-screen attribution and would have to refresh or delete stored API data within 30 days (III.F.2, III.E.4.c).

Two unauthenticated side doors fill part of the gap. The channel feed at `youtube.com/feeds/videos.xml?channel_id=UC…` needs no key and returns the **15 most recent** public uploads, Shorts included ([WP RSS Aggregator](https://finder.wprssaggregator.com/rss-feeds/platform/youtube)). It is undocumented and has been flaky. NewsBlur users saw HTTP 500s from October 2025 ([NewsBlur forum](https://forum.newsblur.com/t/youtube-feeds-broken/13227)). In May 2026 a Hacker News thread described multi-hour outages at about the same time each day and old videos republished with new dates ([HN](https://news.ycombinator.com/item?id=48030964)). A local test on 9 October 2026 found the feed still serving 15 entries with `cache-control: max-age=900`. It also returned intermittent 500s and 404s across eight back-to-back requests, sent no `ETag` or `Last-Modified`, and ignored `If-Modified-Since`. The `UULF` playlist trick that HN commenters recommended for dropping Shorts returned 404 for all three channels tried. Google Takeout supplies the other half: a one-time `subscriptions.csv` under "YouTube and YouTube Music/subscriptions" ([ytsub README](https://github.com/sarowish/ytsub); [Invidious docs](https://docs.invidious.io/export-youtube-subscriptions/)). Watch history comes out only as JSON or HTML. The programmatic Data Portability API requires app verification ([Google](https://developers.google.com/data-portability)).

## Unofficial playback endangers the account and the IP, not the user

Every way of playing YouTube in mpv breaks YouTube's user terms, whether logged in or not. The Terms of Service, effective 15 December 2023, forbid three things: accessing or downloading content unless "expressly authorized by the Service", anything that would "circumvent, disable… or otherwise interfere with any part of the Service", and access "using any automated means" outside public search engines. The stated remedy is that YouTube "reserves the right to suspend or terminate your **Google account**" for material or repeated breach ([YouTube Terms](https://www.youtube.com/t/terms?hl=en&gl=US)). The Paid Service Terms, effective 16 March 2026, separately bar accessing Premium "other than by means authorized by Google" ([Paid Service Terms](https://www.youtube.com/t/terms_paidservice?hl=en)). Premium therefore does not make an unofficial client legitimate. It can only unlock ad-free responses and Premium formats when the account's cookies are passed. Logging out takes the account off the table, which is the main argument for accountless operation. The API Developer Policies bind only developers who accept the API terms. Invidious made exactly that argument when YouTube's legal team gave it a seven-day ultimatum in June 2023, and it kept running ([Michael Tsai](https://mjtsai.com/blog/2023/06/12/youtube-tries-to-shut-down-invidious)).

In practice YouTube enforces against traffic. It followed its 2023 ad-block crackdown with an April 2024 notice: third-party apps that block ads would see buffering or "content is not available on this app", and Premium was "the only way" to go ad-free ([9to5Google](https://9to5google.com/2024/04/15/youtube-app-block-ads/)). Since then the weapons have been technical: "Sign in to confirm you're not a bot" walls, blocks on datacenter and VPN IPs ([Invidious docs](https://docs.invidious.io/youtube-errors-explained/)), PO tokens, SABR-only streams and JavaScript challenges. This research found **no confirmed case of a Google account terminated solely for using yt-dlp, NewPipe, FreeTube, Invidious or SmartTube**. The documented bans involve industrial-scale use. One user downloading "hundreds of audio files per day" switched to cookies from a newly registered account, and that account was "quickly banned" ([yt-dlp #16147](https://github.com/yt-dlp/yt-dlp/issues/16147)). Another, rotating 50–100 cookie sets, saw those accounts blocked ([yt-dlp #11447](https://github.com/yt-dlp/yt-dlp/issues/11447)). yt-dlp's own wiki still warns that logging in risks a temporary or permanent ban and recommends a throwaway account ([yt-dlp wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)). Its observed soft limits are about **300 videos an hour for guests** and 2,000 for accounts. One person browsing interactively stays one to two orders of magnitude below them. The resulting ranking is clear. Logged-in cookie traffic puts the real account at risk. Logged-out traffic risks only an IP soft block, which users report lifting after about an hour to a few days ([yt-dlp #12264](https://github.com/yt-dlp/yt-dlp/issues/12264)). The official API risks only losing API access.

The legal record points the same way: actions have targeted people who distribute or host circumvention tools. The RIAA's §1201 notice took youtube-dl off GitHub on 23 October 2020. GitHub reinstated it on 16 November, promising to "err on the side of the developer" and creating a $1M developer defense fund ([BleepingComputer](https://www.bleepingcomputer.com/news/software/youtube-dl-removed-from-github-after-riaa-dmca-notice/); [GitHub](https://github.blog/news-insights/policy-news-and-insights/standing-up-for-developers-youtube-dl-is-back/)). In Germany, the labels won against Uberspace merely for hosting youtube-dl.org. On **21 November 2024 the Hamburg appeals court (5 U 54/23) held YouTube's "rolling cipher" to be an effective technological measure** and described users of such tools as acting in bad faith ([heise](https://heise.de/-10181247)). §95a(1) UrhG prohibits the act of circumvention itself and has no personal-use carve-out ([§95a UrhG](https://www.gesetze-im-internet.de/urhg/__95a.html)). In the US, Yout's case against the RIAA (2nd Cir. 22-2760) was argued on 5 February 2024 and was still undecided at the docket's 9 September 2026 update ([CourtListener](https://www.courtlistener.com/docket/66697744/yout-llc-v-recording-industry-association-of-america-inc/)). Section 1201(a)(1) bans the act of circumventing an access control. Its trafficking bans in (a)(2) and (b) are what bite on publishing a tool ([17 U.S.C. §1201](https://www.law.cornell.edu/uscode/text/17/1201)). This research found no action against an individual end user. A keyword search of GitHub's DMCA repository found no notice from 2023 to October 2026 against yt-dlp, NewPipe, Invidious, Piped, FreeTube, rustypipe or YouTube.js. Google's own recent notices targeted modified YouTube iOS apps, Play Integrity "pairip" removers (under §1201), and, in June 2026, a repository of "Google's proprietary protocol buffers" ([github/dmca 2024-03-06](https://github.com/github/dmca/blob/master/2024/03/2024-03-06-google.md); [2025-06-24](https://github.com/github/dmca/blob/master/2025/06/2025-06-24-google.md); [2026-06-09](https://github.com/github/dmca/blob/master/2026/06/2026-06-09-google.md)).

Two design consequences follow. First, streaming instead of downloading is not a legal safe harbour. Playing any stream outside YouTube's player requires solving the same signature and "n" challenges the Hamburg court called an effective measure. Leaving out a download button mainly lowers tuitube's profile: NewPipe's download feature is what drew a record label's notice in 2023 ([Gigazine](https://gigazine.net/gsc_news/en/20230713-newpipe-dmca-google-search)). Second, the exposure follows whoever ships the cipher code. A personal, unpublished build avoids the trafficking prongs entirely. If tuitube is ever published, the lowest-exposure shape is a client of public interfaces that shells out to a user-installed yt-dlp and mpv. It never vendors InnerTube `.proto` files or decipher code, and never bundles yt-dlp in release archives. The same split keeps the licences clean. Spawning yt-dlp (Unlicense) and mpv (GPLv2+ by default) as separate programs leaves tuitube MIT, while linking rustypipe (GPL-3.0) or a default libmpv would make the binary copyleft ([yt-dlp LICENSE](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/LICENSE); [mpv Copyright](https://raw.githubusercontent.com/mpv-player/mpv/master/Copyright); [crates.io rustypipe](https://crates.io/crates/rustypipe)).

| Route | Google's position | What account is at risk | Personal legal exposure | What it reaches |
|---|---|---|---|---|
| Data API v3, user's own OAuth client | Sanctioned under the API terms | None beyond losing API access | None | Subscriptions, uploads feeds, 100 searches/day, playlists, comments, writes at 50 units; no playback, Watch Later, history or home feed |
| Channel RSS plus Takeout import | Undocumented, tolerated | None | Negligible | ~15 newest uploads per channel; local subscriptions; no search |
| Accountless yt-dlp + mpv | Breaches user ToS | None (IP soft blocks only) | Theoretical act-of-circumvention question; no recorded enforcement against users | Playback, search, channels, playlists, comments |
| Logged-in via cookies | Breaches ToS, plus the Paid Service Terms for Premium | The real Google account; risk unquantified | Same as above, plus a high-value credential to protect | Adds Watch Later, history, home feed, private playlists, Premium formats |

The defensible design combines the rows instead of choosing one. tuitube is accountless by default, with RSS and Takeout for subscriptions and yt-dlp plus mpv for playback. An optional official OAuth mode syncs subscriptions and playlists. Cookie login exists, at most, as a documented-risk opt-in that keeps the user's main Google account out of the unofficial traffic path.

## yt-dlp alone keeps pace with YouTube's six-to-eight yearly breaks

As of October 2026, logged-out playback across the whole ecosystem rests on a few "native app" InnerTube identities. YouTube still hands these clients direct googlevideo URLs without a PO token. **VISIONOS is now the primary one.** yt-dlp 2026.08.19 added it and dropped `android_vr` from its defaults, after YouTube began returning 403 for every `android_vr` format on 17 August 2026 ([yt-dlp 2026.08.19](https://github.com/yt-dlp/yt-dlp/releases/tag/2026.08.19); [yt-dlp _base.py](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/extractor/youtube/_base.py)). youtubei.js added VISIONOS in 18.0.0 on 13 August ([YouTube.js changelog](https://github.com/LuanRT/YouTube.js/blob/main/CHANGELOG.md)), and NewPipeExtractor's dev branch fetches streams through it too ([NewPipeExtractor](https://github.com/TeamNewPipe/NewPipeExtractor/blob/dev/extractor/src/main/java/org/schabi/newpipe/extractor/services/youtube/extractors/YoutubeStreamExtractor.java)). The web family has been closing since 2025. The WEB client has been SABR-only since February 2025 ([yt-dlp #12482](https://github.com/yt-dlp/yt-dlp/issues/12482)), and MWEB and WEB_EMBEDDED have gone SABR-only in some sessions since September 2026 ([yt-dlp #17666](https://github.com/yt-dlp/yt-dlp/issues/17666)). Logged-in extraction is now *more* fragile than guest extraction. The app clients accept no cookies, and the logged-in default, `tv_downgraded`, has been broken for some users since August ([yt-dlp #17389](https://github.com/yt-dlp/yt-dlp/issues/17389)). Local tests on 9 October 2026 matched this picture. yt-dlp requested only the visionos player response and solved the JS challenges in Deno. youtubei.js got working URLs from VISIONOS (and, intermittently, IOS and ANDROID_VR), a 403 from MWEB without a token, and zero URLs from WEB and TV. Every major extractor converged on one identity within a week. When YouTube closes VISIONOS, every "no PO token, no SABR" path breaks at once.

The countermeasures arrive in waves. In September 2025 yt-dlp announced that YouTube's challenge functions were "spread out all over the player" ([yt-dlp #14404](https://github.com/yt-dlp/yt-dlp/issues/14404)). Since release 2025.11.12, full YouTube support has required an external JavaScript runtime. Without one, support is "deprecated" and format availability is restricted, "severely so in some cases" ([yt-dlp #15012](https://github.com/yt-dlp/yt-dlp/issues/15012)). The minimums rose to Deno 2.3.0 and Node 22 in June 2026 ([yt-dlp 2026.06.09](https://github.com/yt-dlp/yt-dlp/releases/tag/2026.06.09)). Major user-facing outages hit in mid-January, late January, March and August 2026, a pace of roughly six to eight breaking events a year. yt-dlp repaired them quickly. The March "UNPLAYABLE" player block was reported on 11 March and fixed on 13 March ([yt-dlp #16212](https://github.com/yt-dlp/yt-dlp/issues/16212)). The August `android_vr` wipeout was fixed in nightly within a day and in stable on 19 August ([yt-dlp #17456](https://github.com/yt-dlp/yt-dlp/issues/17456)). YouTube now also enforces a pre-roll wait. Stream URLs return 403 until the pre-roll ads that would have played have run their course, and yt-dlp computes and waits out that period ([yt-dlp #17389](https://github.com/yt-dlp/yt-dlp/issues/17389)). An ad-free client still waits out the ad time before the first byte.

| Option | Licence | Activity to October 2026 | 2026 break-and-fix record | Verdict |
|---|---|---|---|---|
| yt-dlp + yt-dlp-ejs (Python) | Unlicense | 10 stable releases Jan–Aug 2026, daily nightlies, ~3.4M PyPI downloads a week | March player block fixed in 2 days; August `android_vr` 403s fixed in 1–2 days | Primary extractor, run as a separate process |
| youtubei.js + BgUtils + googlevideo (TypeScript) | MIT | 18.1.0 on 2026-09-22; no release from Oct 2025 to Mar 2026 | About 1–2 weeks to a library fix for the March break | Fallback sidecar; the only reusable SABR + PO-token stack; needed for writes |
| rustypipe (Rust) | GPL-3.0 | Last release 0.11.4 on 2025-04-23 | March 2026 deobfuscation break unanswered; streams only via IOS, with some 403s | Reject: copyleft and unmaintained |
| innertube-rs (Rust) | MIT | Created 2026-08-24 | No record yet | Watch it; don't depend on it |
| Self-hosted Invidious + companion | AGPL-3.0 | Active (v2.20260804.1) | Needs restarts hourly to daily; datacenter IPs blocked | Reject for a single user |

yt-dlp wins on the property that matters most: recovery speed. It has three active core maintainers plus triage staff ([Maintainers.md](https://github.com/yt-dlp/yt-dlp/blob/master/Maintainers.md)) and shipped ten stable releases in 2026 through August ([releases](https://github.com/yt-dlp/yt-dlp/releases)). Its README calls the daily nightlies "the recommended channel for regular users" ([README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)), and it gets about 3.4 million PyPI downloads a week ([pypistats](https://pypistats.org/packages/yt-dlp)). Because it is a separate program, a fix reaches tuitube without a tuitube release. rustypipe, the only substantial native Rust InnerTube client, fails on both licence and maintenance. It is GPL-3.0, its last release was 0.11.4 on 23 April 2025, and a March 2026 report of "could not extract sig fn name" has gone unanswered ([rustypipe #75](https://codeberg.org/ThetaDev/rustypipe/issues/75)). In a local test its streams worked only partially through the IOS client, and one audio format returned 403. youtubei.js with BgUtils and googlevideo is the only reusable stack that implements SABR and PO tokens today ([googlevideo](https://github.com/LuanRT/googlevideo)), and FreeTube shipped SABR playback on it in April 2026 ([FreeTube releases](https://github.com/FreeTubeApp/FreeTube/releases)). It still needs a JS runtime, though. It lagged yt-dlp by one to two weeks on the March break and went five months without a release over the 2025–26 winter ([releases](https://github.com/LuanRT/YouTube.js/releases)). Feeding SABR to mpv would also need a local proxy that reassembles YouTube's UMP format into a plain stream. That makes it the fallback, and the only path if tuitube ever needs writes such as liking or subscribing, which yt-dlp does not do. Self-hosted Invidious needs PostgreSQL and a Deno companion, without which "playback won't work", plus restarts "at least once a day, ideally every hour" ([Invidious docs](https://docs.invidious.io/installation/)). It adds all that for no robustness gain over yt-dlp. The `innertube-rs` crate, a Rust port of YouTube.js created on 24 August 2026, has no track record yet ([crates.io](https://crates.io/crates/innertube-rs)).

The data layer should start as a per-request yt-dlp subprocess behind a Rust `Backend` trait and grow into a resident helper. Local measurements put a `-J` call on one video at 1.4–2.2 s, a 30-item channel listing at 0.97 s and a 20-result search at 1.10 s. Python startup accounts for only about 0.2 s of that; most of the cost is network time and Deno challenge-solving. A resident Python process reusing one `YoutubeDL` object saves 0.2–0.5 s per call. More importantly, it can hold paging state, so "next page" costs one request instead of re-walking earlier pages. When comments and deep pagination make that matter, move to a small MIT Python helper that imports yt-dlp as a library and speaks tuimeta's newline-delimited JSON protocol. yt-dlp's README documents `extract_info(…, download=False)` plus `sanitize_info` for exactly this use ([README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)). Skip the existing Rust wrappers. The `yt-dlp` crate is GPL-3.0-only and auto-downloads binaries with no stated verification, and `youtube_dl` was last released in April 2024 ([crates.io yt-dlp](https://crates.io/crates/yt-dlp); [crates.io youtube_dl](https://crates.io/crates/youtube_dl)). A hand-written serde model over `-J` is a small job: `Option` fields, unknown fields ignored, and `_version` kept for the doctor screen. Cache metadata aggressively and keep yt-dlp's cache directory persistent so player JS is reused. Never prefetch player responses for highlighted rows, and serialize player requests.

Subscriptions stay in Rust, with RSS first. A `feeds` task fetches through one shared reqwest client, 4–6 requests at a time, and treats `max-age=900` as a floor. It refreshes the stalest channels first, then cycles every 30–60 minutes. It retries 5xx and 404 responses with jittered backoff. After repeated failures it falls back to `yt-dlp --flat-playlist -I 1:15` on the channel's videos tab, or to the Data API's 1-unit `playlistItems.list` when OAuth mode is on. The feed sends no validators, so hashing the body is the only way to skip re-parsing unchanged feeds. feed-rs 3.0.0 (MIT, September 2026) does the parsing ([crates.io feed-rs](https://crates.io/crates/feed-rs)). RSS entries carry no duration, so hiding Shorts needs a `/shorts/` link check or durations from a later flat-playlist pass; don't rely on the `UULF` trick. One optional extra is worth keeping in reserve. The bgutil PO-token provider for yt-dlp, maintained by a yt-dlp maintainer, can rescue sessions where VISIONOS fails and the web clients need tokens. Use version 2.0.0 or later, a security release that fixed remote code execution caused by binding to 0.0.0.0 by default ([bgutil releases](https://github.com/Brainicism/bgutil-ytdlp-pot-provider/releases)). Keep it on localhost and off by default: its own README warns that a token "does not guarantee" success. The development to watch is yt-dlp's SABR downloader, PR #13515, still unmerged at its 4 October 2026 review ([yt-dlp PR #13515](https://github.com/yt-dlp/yt-dlp/pull/13515)).

## mpv runs as a locked-down child fed URLs tuitube resolved

For a one-person project, spawning the system mpv and driving it over JSON IPC beats embedding libmpv on every point that matters. mpv is GPLv2+ by default and LGPL only when built without GPL files ([mpv Copyright](https://github.com/mpv-player/mpv/blob/v0.41.0/Copyright)). The maintained Rust binding, libmpv2 6.0.0, is itself LGPL-2.1 and needs a system libmpv on each of six targets ([crates.io libmpv2](https://crates.io/crates/libmpv2)). A separate process also keeps FFmpeg parser crashes out of the TUI. The IPC protocol is one JSON object per line, with integer `request_id`s and events interleaved on the same stream ([mpv ipc.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/ipc.rst)). That is small enough for a 200–300-line tokio client, which also avoids `mpvipc`, a GPL-3.0 crate ([crates.io mpvipc](https://crates.io/crates/mpvipc)).

The IPC channel must be private. mpv's manual calls it "explicitly insecure: there is no authentication, no encryption", and it exposes a `run` command "which can run arbitrary system commands" ([mpv ipc.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/ipc.rst)). On Unix the clean answer is `--input-ipc-client=fd://3` with a `socketpair()` whose child end mpv inherits. No filesystem socket exists for another process to find, and macOS's ~104-byte `sun_path` limit never applies. "The player quits when the connection is closed", so a crashed tuitube never leaves a remote-controllable player behind ([mpv options.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/options.rst)). On Windows, use a random pipe name per launch. mpv already restricts its pipe to the current user's SID at the same integrity level and rejects remote clients ([mpv ipc-win.c](https://github.com/mpv-player/mpv/blob/v0.41.0/input/ipc-win.c)), and tokio provides the client side ([tokio docs](https://docs.rs/tokio/latest/tokio/net/windows/named_pipe/index.html)). Avoid ytsub's predictable `<pid>-<n>` socket name in the shared temp directory ([ytsub mpv/mod.rs](https://github.com/sarowish/ytsub/blob/HEAD/src/mpv/mod.rs)). Never use Linux `@abstract` socket names, which have no filesystem permissions at all. tuitube's IPC client should expose only typed commands (pause, seek, volume, observe property, load a resolved URL) and never forward user-typed or remote text as an mpv command.

The research notes disagreed on who should resolve streams, and tuitube should resolve them itself. mpv's ytdl_hook is simpler: hand mpv a watch URL, and it runs yt-dlp and combines the separate audio and video tracks into an EDL. But that second yt-dlp runs without `--ignore-config`, gets every `ytdl-raw-options` entry appended verbatim, and is found by searching PATH and mpv's config directory ([ytdl_hook.lua](https://github.com/mpv-player/mpv/blob/master/player/lua/ytdl_hook.lua); [mpv options.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/options.rst)). Resolving in tuitube means a single hardened yt-dlp invocation and full control over quality, chapters, titles and resume. tuitube then passes googlevideo URLs to mpv with `--ytdl=no`, ideally over IPC with `loadfile` and `audio-add` after spawn, so signed URLs never show up in `ps`. The price is managing expiry. In a local test, every https googlevideo URL carried an `expire` exactly 6 hours ahead and an `ip=` parameter, so tuitube must re-resolve on a 403, after six hours, or after a network change. The same test showed mpv printing the **full signed URL** to its terminal output when the URL was used as an external audio track, which makes `--terminal=no` mandatory. Keep ytdl_hook as a fallback, with `--script-opts=ytdl_hook-ytdl_path=<absolute path>` and `--ytdl-raw-options=ignore-config=,no-plugin-dirs=`. If YouTube makes every tokenless client SABR-only, both paths fail together. The HLS formats are the likeliest survivors, since the PO Token Guide says web_safari's HLS formats currently need no token ([PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)).

Launch mpv from an argv vector, never a shell, with `--no-config --load-scripts=no --osc=no --input-terminal=no --terminal=no --idle=yes --save-position-on-quit=no --hwdec=auto --ytdl=no --input-ipc-client=fd://3`. Add the individual `--load-*=no` toggles for the built-in console, stats, select, positioning, context-menu and auto-profile scripts. `--no-config` blocks mpv.conf, input.conf, user scripts and resume files ([mpv options.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/options.rst)). A local test confirmed this: a planted `scripts/probe.lua` and `mpv.conf` loaded by default and stopped loading with the flag. If the user wants keys inside the video window, keep the built-in bindings or ship a tuitube-owned `--input-conf`; never load the user's input.conf. Offer "use my mpv config" as an opt-in for people who want shaders or uosc, with a warning that their scripts run with mpv's privileges and can observe everything tuitube sends. Always choose formats explicitly. In the local test, yt-dlp's default picked AV1 2160p with Opus, which many machines cannot hardware-decode. A sensible default is `bv*[height<=1080][vcodec^=avc1]+ba[acodec^=mp4a]/bv*[height<=1080]+ba/b` with a configurable height cap. Pass `--hwdec=auto` explicitly, because `--no-config` discards the user's setting. Keep resume in tuitube. mpv's watch-later files are keyed on a hash of the full path, which changes with every resolve, so observe `time-pos`, store it per video ID, and pass `start=` when loading.

Version skew is the main portability trap. mpv 0.41.0 (December 2025) is current on Homebrew, Arch, Fedora 44 and Ubuntu 26.04, but Ubuntu 24.04 ships 0.37.0 and Debian 12 ships 0.35.1 ([Repology](https://repology.org/project/mpv/versions)). mpv 0.38 inserted an index argument into `loadfile` that "breaks all existing uses" that pass per-file options ([mpv input.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/input.rst)). Read `mpv-version` at connect time and build the command to match, or set properties before loading. Require mpv 0.35 or later and prefer 0.38 or later. On macOS the install is one command, since Homebrew's mpv formula depends on yt-dlp and yt-dlp's depends on Deno ([Homebrew mpv](https://formulae.brew.sh/formula/mpv); [Homebrew yt-dlp](https://formulae.brew.sh/formula/yt-dlp)). A `tuitube doctor` screen should print the resolved paths and versions of mpv, yt-dlp, Deno and FFmpeg.

Two playback extras should wait. mpv can draw video inside the terminal through its kitty, sixel and tct outputs, but each is software-scaled, the docs repeatedly suggest `--profile=sw-fast`, and the output fights ratatui for the same TTY ([mpv vo.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/vo.rst)). It makes a fun opt-in preview mode, not the default. In-process audio could reuse tuigram's cpal stack through symphonia. Symphonia decodes AAC-LC in MP4 well but has no native Opus decoder ([Symphonia](https://github.com/pdeljanov/Symphonia)), so it would play itag 140 (m4a, about 128 kbps). It would also mean rebuilding mpv's caching, reconnects and HTTP-range seeking, so v1 should play audio-only through mpv with `--vid=no`.

Thumbnails reuse tuigram's ratatui-image code; the crate is at 11.1.0 stable, with 12.0 in release candidates ([crates.io ratatui-image](https://crates.io/crates/ratatui-image)). Use `mqdefault` (320×180, 16:9, no letterbox) for list rows. For detail panes, use `hq720` or `maxresdefault` with an `hqdefault` fallback. Prefer the `/vi_webp/` variants, which were 45–56% smaller in a local test. Always check the HTTP status. In the same test, an old video's `maxresdefault.jpg` returned 404 *with a valid 120×90 placeholder image* in the body, which would otherwise render silently as a grey box. Decode off the UI task with ratatui-image's `ThreadProtocol`, because resizing "is blocking" ([ratatui-image README](https://github.com/ratatui/ratatui-image)).

## tuimeta's helper frame and tuigram's discipline shape the processes

The process picture is four cooperating programs, with tuitube the single owner of state.

| Process | Code and licence | Job | Network it needs | Containment |
|---|---|---|---|---|
| `tuitube` | Rust, MIT | UI, SQLite state, RSS polling, thumbnails, mpv control, optional OAuth Data API calls | `www.youtube.com/feeds`, `i.ytimg.com`, `yt3.ggpht.com`; `googleapis.com` only in OAuth mode | 0700 data dir; never executes remote strings |
| `yt-dlp` (per request; later a resident MIT Python helper that imports it) | Python, Unlicense, user-installed and version-pinned | Search, channels, playlists, comments, stream resolution | `www.youtube.com` (InnerTube) | No config or plugins, cleared env, private CWD; sandboxed later |
| `deno` (spawned by yt-dlp) | Deno ≥ 2.3, launched with no permissions | Solves YouTube's n/sig JavaScript challenges | None | Deno default-deny; no secrets in its env |
| `mpv` | C on FFmpeg, GPLv2+, user-installed | Plays resolved googlevideo URLs in its own window or audio-only | `*.googlevideo.com` | `--no-config`, socketpair IPC, typed commands only |
| `bgutil` PO-token provider (optional) | GPL-3.0 third-party plugin | Mints PO tokens if VISIONOS stops working | Google's BotGuard attestation | Off by default, ≥ 2.0.0, localhost only |

Inside tuitube, keep tuimeta's skeleton. One `tokio::select!` waits on backend events, image encodes, mpv IPC, terminal input and signals; "each wake drains the event backlog, then redraws", and all state lives in `App`. Keys route to the first modal layer, Normal or Insert, and `:` commands take full names with Tab completion, which gives the vim feel for free ([tuimeta CLAUDE.md](https://github.com/erictran308/tuimeta/blob/main/CLAUDE.md)). Shape the `Backend` trait like the future helper protocol from day one, so swapping per-request subprocesses for a resident helper changes no view code. Copy tuimeta's protocol frame unchanged: one JSON object per line with an integer `id` chosen by the front end, exactly one `result` or `error` per request, a first-line `hello` carrying a protocol `version` that the front end refuses if it doesn't know it, exit within two seconds of stdin closing, and nothing but protocol lines on stdout ([tuimeta PROTOCOL.md](https://github.com/erictran308/tuimeta/blob/main/helper/PROTOCOL.md)). Three changes fit YouTube. IDs stay as YouTube's own public strings but are validated against `^[A-Za-z0-9_-]{11}$` for videos, `^UC[A-Za-z0-9_-]{22}$` for channels, and the known prefixes for playlists. An explicit `cancel` lets typing in search abort the previous query. Every list call returns an opaque `continuation` owned by the helper, which becomes invalid when the helper restarts. The method set is small: `search`, `suggest`, `channel`, `playlist`, `video`, `streams`, `comments`, `related`, `feed` (the RSS fallback), `resolve` and `backend`. Add five error codes to tuimeta's list: `unavailable`, `age_restricted`, `rate_limited`, `backend_missing`, and `outdated` (which tells the user to update yt-dlp). Drop stale answers exactly as tuimeta does: each request carries what was asked, each helper start gets a generation number, and anything that doesn't match is discarded. A deterministic `--fake` mode keeps ratatui `TestBackend` tests offline.

Local state follows the sibling apps. The data directory is `dirs::data_local_dir()/tuitube`, forced to 0700 on every start. An override is accepted only if it passes tuigram's `private_place` check: every ancestor is owned by the user or root, nothing is writable by others, and on macOS group-writable counts as others, because "every account is in `staff`" ([tuigram config.rs](https://github.com/erictran308/tuigram/blob/main/src/config.rs)). `settings.toml` stays 0600. It is written to `.toml.new`, synced, then renamed over the old file, as tuimeta's `Settings::save` does ([tuimeta settings.rs](https://github.com/erictran308/tuimeta/blob/main/src/settings.rs)). Everything that grows or gets queried goes into one `tuitube.db` through rusqlite 0.40 with the `bundled` feature ([crates.io rusqlite](https://crates.io/crates/rusqlite)): channels with their feed health, videos, watch-later, history and resume positions. Create the file with mode 0600 before opening it in WAL mode, so the `-wal` and `-shm` files are private too. Run database work on one dedicated thread, and debounce resume writes to every 5–10 seconds plus pause and stop. Offer `:export` and `:import` of subscriptions as OPML or channel-ID lines, so the data is never locked in.

tuitube's own HTTP is limited to feeds, thumbnails and, in OAuth mode, googleapis.com. Use reqwest 0.13, whose default TLS is now rustls with aws-lc-rs and the platform verifier ([docs.rs reqwest](https://docs.rs/crate/reqwest/latest/features)). There is no evidence that YouTube gates on TLS fingerprints. yt-dlp's YouTube extractor impersonates a browser only for subtitle downloads ([yt-dlp _video.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_video.py)), and curl's non-browser TLS stack got 200s from InnerTube and RSS in local tests. Neither tuigram nor tuimeta has an HTTP client today, so this is a new dependency to audit. aws-lc-rs also needs a C toolchain on some targets; the `ring` provider avoids that.

About a fifth of tuimeta's 22,228 lines carries over almost unchanged: `text.rs`, `config.rs`, `settings.rs`, `theme.rs`, `clipboard.rs`, `tmux.rs`, `complete.rs`, the help table, `notify.rs` (for "N new videos" batching) and the panic hook. `images.rs`, the viewer, the two-phase picker and the helper plumbing in `meta.rs` carry over with moderate edits. Chat state, message views, reactions and attachments become feed, list, video-detail, comments and player-bar views. ytsub is the closest existing architecture, with local InnerTube, SQLite, mpv over IPC and Takeout import ([ytsub](https://github.com/sarowish/ytsub)). But ytsub and youtube-tui are both GPL-3.0, so read them for ideas and copy no code into an MIT tree. For distribution, "personal use only" argues for tuimeta's model (GitHub only, `publish = false`) or a private repository. If tuitube is ever shared, borrow tuigram's release mechanics, including six targets and SHA-256-pinned native downloads ([tuigram release.yml](https://github.com/erictran308/tuigram/blob/main/.github/workflows/release.yml)), but never bundle yt-dlp or Deno into the archives.

## Integration choices, not exotic exploits, decide tuitube's security

Real incidents in the YouTube-client ecosystem fall into a few classes, and each one maps to a rule. Untrusted metadata reached a shell or a terminal: yt-dlp's `--exec` CVEs and mpv's 2026 terminal-injection advisory. Untrusted import files ran code: NewPipe's backup deserialization and newsboat's OPML import. A planted binary got executed: Anki. A client's own updater shipped malware: SmartTube. None of these needed a novel exploit, only a convenient integration choice.

| Surface | Rule | Motivating incident or source |
|---|---|---|
| Process launch | `tokio::process::Command` argv vectors only, never a shell; `--` before every positional URL; never `.cmd`/`.bat` shims on Windows | yt-dlp `--exec` injection ([CVE-2023-40581](https://nvd.nist.gov/vuln/detail/CVE-2023-40581)); YoutubeDLSharp argument injection ([CVE-2025-43858](https://nvd.nist.gov/vuln/detail/CVE-2025-43858)); Rust batch-file escaping ([CVE-2024-24576](https://ubuntu.com/security/CVE-2024-24576)) |
| Binary resolution | Absolute pinned paths for yt-dlp, Deno and mpv, recorded with SHA-256 in a `tools.lock` checked at startup; never search the CWD or a media folder | Anki ran a planted `yt-dlp.exe` from a shared deck ([CVE-2025-62185](https://nvd.nist.gov/vuln/detail/CVE-2025-62185)); Rust stopped searching the CWD on Windows only in 1.58 ([Rust blog](https://blog.rust-lang.org/2022/01/13/Rust-1.58.0/)) |
| IDs and URLs | Regex-validate IDs; build `https://www.youtube.com/watch?v=<id>` in Rust; pass mpv only allowlisted googlevideo URLs; never pass a URL taken from remote data to a subprocess | Video IDs can start with `-`, and mpv accepts legacy `-option` syntax ([mpv.rst](https://github.com/mpv-player/mpv/blob/master/DOCS/man/mpv.rst)); yt-dlp URL smuggling, CVE-2023-46121 ([yt-dlp security](https://github.com/yt-dlp/yt-dlp/security)) |
| yt-dlp | No config, plugins or remote components; cleared env; private CWD; resolve-only. Never `--exec`, `--netrc-cmd`, `--write-link`, external downloaders, output templates built from metadata, `--cookies-from-browser` or `-U` | 13 advisories from 2023 to 2026, nearly all in those features ([OSV](https://osv.dev/list?ecosystem=PyPI&q=yt-dlp)) |
| mpv | `--no-config --load-scripts=no --terminal=no`; typed IPC allowlist; socketpair or current-user pipe | IPC exposes `run` ([ipc.rst](https://github.com/mpv-player/mpv/blob/v0.41.0/DOCS/man/ipc.rst)); terminal injection via metadata ([GHSA-546v-22c3-7927](https://github.com/mpv-player/mpv/security/advisories/GHSA-546v-22c3-7927)) |
| Remote text | `text::clean` on every remote string before render, copy or notification, with length caps | Ghostty title injection ([CVE-2024-56803](https://nvd.nist.gov/vuln/detail/CVE-2024-56803)); ANSI injection in tracing-subscriber ([CVE-2025-58160](https://nvd.nist.gov/vuln/detail/CVE-2025-58160)) |
| Images | Pure-Rust JPEG and WebP only; strict dimension and byte caps; contained panics; allowlisted hosts | libwebp heap overflow exploited in the wild ([CVE-2023-4863](https://osv.dev/vulnerability/CVE-2023-4863)) |
| Imports | Strict schemas for Takeout CSV, NewPipe JSON and OPML; accept only channel IDs and youtube.com URLs | NewPipe backup RCE ([GHSA-wxrm-jhpf-vp6v](https://github.com/TeamNewPipe/NewPipe/security/advisories/GHSA-wxrm-jhpf-vp6v)); newsboat OPML `exec:` URLs ([GHSA-4m8m-vj3m-hfxx](https://github.com/newsboat/newsboat/security/advisories/GHSA-4m8m-vj3m-hfxx)) |
| Logs | Never log googlevideo URLs, cookies, PO tokens, titles, queries or IDs; redact `sig`, `lsig`, `pot` and `ip` | mpv printed a full signed URL (local test); tuimeta's "no message text in logs" rule ([PROTOCOL.md](https://github.com/erictran308/tuimeta/blob/main/helper/PROTOCOL.md)) |
| Credentials | No browser extraction; throwaway account; 0600 file or keyring-wrapped; passed only as a `--cookies` path | yt-dlp reads, then rewrites, the whole browser jar ([cookies.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/cookies.py)) |
| Watch signals | One `report_watch` gate: default off, logged-in only | yt-dlp's `_mark_watched` history pings ([_video.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_video.py)) |

The yt-dlp invocation deserves the most care, because yt-dlp is where hostile input gets parsed. Most of its CVEs live in features tuitube never needs: `--netrc-cmd` (CVE-2026-26331), the aria2c and curl downloaders (CVE-2026-50574, CVE-2026-50019), and `--write-link` ([CVE-2026-55404](https://nvd.nist.gov/vuln/detail/CVE-2026-55404)). The structural risks are silent configuration and plugins. yt-dlp reads a "home" config from the current directory when `-P` isn't given. "All plugins are imported even if not invoked, and… there are no checks performed on plugin code" ([yt-dlp README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)). Run yt-dlp from a fresh 0700 working directory, with the environment cleared to `PATH`, `HOME`, `LANG` and `YTDLP_NO_PLUGINS=1`. Pass `--ignore-config --no-plugin-dirs --no-remote-components --no-js-runtimes --js-runtimes deno:<absolute path> --cache-dir <private dir> -J -- <canonical URL>`. Because tuitube only resolves, yt-dlp's downloaders, the source of most of its CVEs, never run. Deno is the right runtime. yt-dlp launches it with no `--allow-*` flags, `--no-remote` and the script on stdin ([deno.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/jsc/_builtin/deno.py)). Bun, by contrast, runs unrestricted, and QuickJS writes a temp file per run that "could enable a TOCTOU vulnerability" ([EJS wiki](https://github.com/yt-dlp/yt-dlp/wiki/EJS)). Deno's 2025–2026 permission bypasses mostly involve partial grants, which yt-dlp never makes ([OSV](https://osv.dev/list?ecosystem=crates.io&q=deno)). yt-dlp copies its whole environment into Deno, so nothing secret may ever sit in yt-dlp's environment.

Updates are where freshness and safety pull against each other. yt-dlp calls its stable channel "often 'stale'" and recommends nightly, and fixes land within days, so tuitube cannot freeze a version for months. But `yt-dlp -U` verifies only a SHA-256 list fetched from the same release; `update.py` does no GPG check ([update.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/update.py)). And SmartTube showed in late 2025 how a compromised build machine turns a built-in updater into a malware channel ([BleepingComputer](https://bleepingcomputer.com/news/security/smarttube-youtube-app-for-android-tv-breached-to-push-malicious-update)). The answer is a deliberate `:ytdlp update` command. It fetches the chosen channel's binary and verifies `SHA2-256SUMS` against the GPG-signed `SHA2-256SUMS.sig` and yt-dlp's published key ([README](https://github.com/yt-dlp/yt-dlp/blob/master/README.md)). It shows the new version and the verification result, then records the new hash in `tools.lock`. tuitube warns when its yt-dlp is more than 90 days old, only checks and warns when Homebrew or pip owns the binary, and never runs `-U` itself.

Every string YouTube returns is attacker-controlled, and terminal escape injection keeps producing real CVEs. Ghostty 1.0.0 executed a window title that a terminal escape sequence reported back onto the command line ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2024-56803)). Rust's `tracing-subscriber` passed ANSI sequences through from logged input ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-58160)). mpv's May 2026 advisory showed media metadata spoofing terminal content and overwriting the clipboard via OSC 52 ([GHSA-546v-22c3-7927](https://github.com/mpv-player/mpv/security/advisories/GHSA-546v-22c3-7927)). tuimeta's `text::clean` strips control characters, bidi overrides, invisible characters and kitty's placeholder. It should run on every title, channel name, description, comment, chapter, caption line and stderr message before display, copy or notification. Links need one YouTube-specific twist. Description and comment links arrive wrapped as `youtube.com/redirect?…&q=<target>`, with truncated display text ([rustypipe util](https://codeberg.org/ThetaDev/rustypipe/src/branch/main/src/util/mod.rs)). tuitube should unwrap them locally and flag a link as disguised only when its display text looks like a URL whose host differs from the target's. Links to `/watch`, `/@handle`, `/channel/UC…` and `/playlist` should become in-app navigation, not handed to the OS. Show the `@handle` next to the display name, and draw the verified mark only from a structured field, in a colour a channel name cannot produce, so a name ending in "✓" cannot pass as verified.

Media and images are parser attack surface. FFmpeg fixes memory-safety bugs in every release, and two recent ones hit formats YouTube actually serves: an out-of-bounds write in DASH manifest handling ([CVE-2025-59728](https://osv.dev/vulnerability/CVE-2025-59728)) and an out-of-bounds read in the AV1 decoder ([CVE-2026-30997](https://osv.dev/vulnerability/CVE-2026-30997)). Treat mpv as untrusted once it opens media, keep it updated through the package manager, and give it nothing worth stealing. For thumbnails, the C precedent is libwebp's CVE-2023-4863, which CISA added to its Known Exploited Vulnerabilities catalog a day after publication ([OSV](https://osv.dev/vulnerability/CVE-2023-4863)). Build the `image` crate with `default-features = false, features = ["jpeg", "webp"]`, both pure-Rust decoders, rather than its fourteen-format default. Never enable `avif-native`, which links the C library libdav1d ([image Cargo.toml](https://github.com/image-rs/image/blob/main/Cargo.toml)). `max_alloc` "is non-strict by default and some decoders may ignore it" ([docs.rs image::Limits](https://docs.rs/image/latest/image/struct.Limits.html)), so rely on strict width and height limits, a byte cap checked against `Content-Length`, and tuimeta's contained-panic decoding.

If tuitube ever logs in, the credential is the whole Google account. Google's SID and HSID cookies hold "digitally signed and encrypted records of a user's Google Account ID" and last two years ([Google](https://policies.google.com/technologies/cookies)). Google's Threat Analysis Group has documented "pass-the-cookie" malware campaigns hijacking YouTube creator accounts since 2019 ([Google TAG](https://blog.google/threat-analysis-group/phishing-campaign-targets-youtube-creators-cookie-theft-malware/)). Microsoft counted over 394,000 Windows machines infected by the Lumma infostealer in two months of 2025 ([Microsoft](https://blogs.microsoft.com/on-the-issues/2025/05/21/microsoft-leads-global-action-against-favored-cybercrime-tool/)). Google itself says "there is no reliable way to prevent cookie exfiltration using software alone" ([Google Security blog](https://blog.google/security/protecting-cookies-with-device-bound-session-credentials/)). Its answer is Device Bound Session Credentials (DBSC), generally available and on by default in Chrome on Windows for personal Google accounts since 28 May 2026 ([Google Workspace Updates](https://workspaceupdates.googleblog.com/2026/05/prevent-account-takeovers-with-DBSC-now-generally-available-in-the-Chrome-browser-for-Windows.html)). DBSC binds sessions to a key that cannot leave the machine, so copied cookies are designed to stop working quickly, and YouTube already rotates cookies on any open tab ([yt-dlp wiki](https://github.com/yt-dlp/yt-dlp/wiki/Extractors)).

Never call `--cookies-from-browser`. Its Chromium path selects every cookie in the profile, with no WHERE clause, and can trigger a Keychain prompt. Combined with `--cookies`, it writes the entire browser jar to disk, because yt-dlp dumps its jar back into the cookie file ([cookies.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/cookies.py)). An opt-in login should copy tuimeta's cookie paste. The user exports a Netscape cookies.txt from a single private window signed in to a throwaway account. tuitube masks the input, filters it to `.youtube.com`, checks that the required cookie names are present, and stores it 0600 in the 0700 data dir. Alternatively it encrypts the file under a random key wrapped by the OS keystore, as the tuigram Meta report recommended, using keyring 4.2's per-platform stores ([docs.rs keyring](https://docs.rs/keyring/latest/keyring/)). The cookies reach yt-dlp only as a `--cookies` path, never through argv or the environment. yt-dlp rewrites that file with rotated values, so it is the live copy. Use cookies only for account feeds (subscriptions feed, Watch Later, history, liked videos) and keep resolving ordinary streams logged out, which current client behaviour favours anyway. Do not copy rustypipe's OAuth. It impersonates YouTube's TV client, requests the full `youtube` scope, and caches tokens in the current working directory ([rustypipe client](https://codeberg.org/ThetaDev/rustypipe/src/branch/main/src/client/mod.rs)). For account data, the least-privilege route is the official `youtube.readonly` scope with the user's own project.

tuitube needs one privacy gate, the YouTube equivalent of tuigram's read receipts. YouTube's watch-history and watch-time signals are the `videostatsPlaybackUrl` and `videostatsWatchtimeUrl` pings in the player response. yt-dlp sends them only with `--mark-watched`, which is off by default; its source comments that they "seem to mark watchtime 'history' in the real world" ([yt-dlp _video.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/youtube/_video.py)). YouTube.js sends them only through explicit `addToWatchHistory()` and `updateWatchTime()` calls ([MediaInfo.ts](https://github.com/LuanRT/YouTube.js/blob/main/src/core/mixins/MediaInfo.ts)). In tuitube, only one function, `App::report_watch`, may ever send them. It fires only when the user is logged in and has switched on "sync watch history" (default off), only after real playback, and never for prefetch or autoplay. Tests with fake yt-dlp and mpv binaries should assert that `--mark-watched` never appears in argv unless that gate fired.

The remaining signals are unavoidable but can be kept small. A player request reveals which video was opened, so resolve only on Enter. Thumbnail fetches reveal which rows were displayed, so fetch lazily and offer a no-thumbnails mode. Visitor data, now the six-month `__Secure-YNID` cookie ([Google](https://policies.google.com/technologies/cookies)), links guest sessions together. Default to fresh visitor data per launch, accepting slightly more bot checks for less linkability. Keep history local, in a 0600 store with pause and clear keys. Make SponsorBlock, DeArrow and Return YouTube Dislike opt-in, since each one sends video IDs to a third party. A proxy or Invidious instance only moves trust: Invidious's own FAQ notes that instance owners "can log your IP address" ([Invidious FAQ](https://docs.invidious.io/faq/)).

The Rust side needs tuigram's supply-chain controls from day one. On 20 August 2026, attackers republished the long-established `arrayref` crate with a build-script dropper and yanked its legitimate versions; the malicious versions were live for under two hours ([RUSTSEC-2026-0264](https://rustsec.org/advisories/RUSTSEC-2026-0264); [StepSecurity](https://www.stepsecurity.io/blog/arrayref-rust-crate-supply-chain-attack)). Build with `--locked` and run cargo-deny against advisories, licences and sources. Schedule a weekly RustSec check so advisories like rustls's of 14 September 2026 surface without a code change ([OSV](https://osv.dev/vulnerability/RUSTSEC-2026-0285)). Use cargo-vet with a rule that any new crate carrying a `build.rs` or proc-macro gets a manual look ([cargo-vet](https://mozilla.github.io/cargo-vet/)). Pin every GitHub Action to a full commit SHA: the 2025 tj-actions compromise repointed version tags, and SHA-pinned users stayed safe ([Orca Security](https://orca.security/resources/blog/github-action-tj-actions-changed-files-compromised/)). GitHub has been able to enforce SHA pinning since 15 August 2025 ([GitHub changelog](https://github.blog/changelog/2025-08-15-github-actions-policy-now-supports-blocking-and-sha-pinning-actions/)). Publish build provenance with `actions/attest` ([GitHub Docs](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)).

Sandboxing comes last, as defence in depth, because the hardened argv, environment and flags already cover most of the real risk. The first step after them is an allowlisting CONNECT proxy that the child processes reach through `HTTPS_PROXY`, allowing only `www.youtube.com`, `*.googlevideo.com` and the thumbnail hosts and logging every host contacted for privacy audits. Next comes Landlock on Linux, with filesystem rules plus TCP connect limited to the proxy's port, since Landlock network rules can only name ports, not hosts ([kernel docs](https://docs.kernel.org/userspace-api/landlock.html)). Then `sandbox-exec` on macOS, and finally an AppContainer with a kill-on-close job object on Windows ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer)). Apple marks `sandbox-exec` deprecated and says it was never documented for third-party use ([Apple forums](https://developer.apple.com/forums/thread/777509)). Even so, a local test on macOS 27.2 showed it still enforcing a network deny and a `~/.ssh` read deny. It accepts only `*` or `localhost` as a network host, which is why the proxy is needed. If Apple removes it, tuitube must say so in the status bar rather than fall back silently.

## Conclusion

The strongest security property of this design is what it leaves out. With no Google account, no stored credential and no cipher code in tuitube's own binary, the realistic worst cases are small. One is an IP soft block lasting an hour or a few days. Another is a broken extractor, fixed by updating one verified binary. The third is an FFmpeg parser bug in a child process that holds nothing worth stealing. Every feature that adds an account back (cookies, writes, history sync) also brings back the one thing YouTube can actually take away, and the trend runs against such features. DBSC is designed to make copied cookies stop working, the app clients that still serve plain URLs refuse cookies, and the logged-in default client has been broken since August. The official API is the only durable route to account data, and it is a sync tool, not a player.

The fragility sits in one place, so the architecture should be built around it. As of October 2026, plain-URL playback depends on VISIONOS surviving. When that client falls, the likely successor is yt-dlp's SABR downloader feeding mpv through a pipe or a local proxy rather than a URL. tuitube's player module should therefore accept "a stream source" (URLs, an HLS manifest, or a byte pipe from yt-dlp) instead of assuming googlevideo URLs, which keeps that change inside one module. Some questions remain open. The account-ban probability for light logged-in use is unmeasured, the RSS endpoint's future is undocumented, and the local tests here are a single-IP snapshot. Before tuitube is ever published rather than kept personal, check two things: whether the Second Circuit has ruled in Yout v. RIAA, and whether Germany's Federal Court of Justice took up the Uberspace case. Either could change the legal exposure of shipping even a thin yt-dlp front end.

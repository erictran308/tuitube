# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

tuitube: a terminal YouTube client for one person's own use, with a YouTube-like layout (sidebar + grid of video cards) and both arrow keys and vim keys. Rust, ratatui, tokio, MIT. A sibling of tuigram (`../tuigram`, Telegram) and tuimeta (`../tuimeta`, Meta's messengers): same security posture, same themes, same `text::clean`, config and settings code. The research behind every design choice is `reports/YouTube terminal client.md` (notes in `research_notes/`); read its security section before changing how programs are started or what is sent to YouTube.

No Google account, ever, in this version: subscriptions are local (imported from Google Takeout's `subscriptions.csv`), refreshed from public channel RSS feeds. Don't add cookie login or `--cookies-from-browser`: Google cookies are the whole Google account (Gmail, Drive), and YouTube's terms let it suspend the account. tuitube contains none of YouTube's cipher or InnerTube code; yt-dlp (a separate program) does that.

## Running

Running tuitube is safe (no account), but it talks to YouTube and mpv opens windows and plays sound. For checks, prefer tests that render into ratatui's `TestBackend` (`ui/mod.rs` tests). Use a separate data folder for trying things: `TT_DATA_DIR=$HOME/tt-test cargo run` (a full path in your own home: `/tmp` is shared, and relative paths are refused). `tuitube --demo` (`demo.rs`) fills the real UI with made-up channels and videos, preloaded pictures drawn in code, an in-memory store and `App.demo` set: nothing is fetched or played. `docs/hero.png` is one frame of it: `cargo test -- --ignored export_hero_screen` writes `target/hero/screen.json` (cells, colors, where `Images::placed` says each picture went), and `tools/hero.py` draws it as Ghostty would (JetBrains Mono, Nerd Font icons, box lines drawn to the cell edges). Tests that talk to YouTube, sponsor.ajay.app or run mpv are `#[ignore]`d: `cargo test -- --ignored live` (logged out, a handful of requests; the mpv ones play generated silence).

## Commands

```sh
cargo build
cargo test                       # offline tests
cargo test -- --ignored live     # against YouTube, sponsor.ajay.app and the real mpv
cargo clippy --all-targets       # keep it warning-free
cargo fmt
cargo run -- --import path/to/subscriptions.csv
```

Needs `yt-dlp`, `deno` and `mpv` at run time (`brew install yt-dlp deno mpv`). `tools::Tools::find` resolves each to an absolute path once (settings `yt_dlp`/`mpv`/`deno`, `TT_YT_DLP`/`TT_MPV`/`TT_DENO`, else absolute `PATH` entries, then Homebrew/system folders); a program is never started by bare name. `main` (a plain `fn`, before the tokio runtime or any thread) also cuts tuitube's own `PATH` down to its absolute entries (`tools::absolute_path_entries`), because code it uses starts programs by name (ratatui-image's `tmux`, crossterm's `tput`, xdg-open's helpers): none can come from the folder tuitube was started in. `.env` is read only by development builds, only from the source folder (`CARGO_MANIFEST_DIR`, never the working directory: some `TT_*` keys name programs to run) and only `TT_*` keys (`config::load_dotenv`, never the process environment). The data dir (`TT_DATA_DIR`, a full path, or the platform app-data dir; `tuitube --help` prints it) is made by `config::make_private_dir`: the folders above it checked first (`private_place`: changeable only by you or root, owners compared with `geteuid`), then the folder made 0700 or found to be a real folder of yours (never a link), set 0700, and on macOS cleared of inherited ACLs (`/bin/chmod -RN`); on Windows a `TT_DATA_DIR` must be in the user profile. It holds `tuitube.db` (SQLite, 0600), `settings.toml` (0600, written through a rename of a per-process temp file), `cache/images`, `cache/yt-dlp` and `work/` (yt-dlp's working directory).

## Releasing

Release binaries are built only by `.github/workflows/release.yml` (pushing a `v*` tag): six targets (Linux on Ubuntu 22.04 for a glibc 2.35 floor, macOS, Windows with a static C runtime; x86_64 and ARM64 each), tests run on the native ones, then the GitHub release gets the archives, `SHA256SUMS` and a provenance attestation covering both. `cargo binstall tuitube` takes those archives (`[package.metadata.binstall]` in `Cargo.toml`), so asset names and the `v<version>` tag must stay as `pkg-url` expects, and the release must be up before `cargo publish`. `.github/workflows/ci.yml` runs fmt, clippy (`-D warnings`) and tests on Linux, macOS and Windows for every push, and `cargo audit` weekly.

1. Bump `version` in `Cargo.toml`, run `cargo build` (updates `Cargo.lock`), then tests, clippy, `cargo fmt --check` and `actionlint`.
2. Commit and push `main`; wait for CI.
3. Write a short changelog (a few bullets, for users) to a file outside the repo, then `git tag -a vX.Y.Z --cleanup=whitespace -F <file> && git push origin vX.Y.Z` (without `--cleanup`, git drops `#` lines such as Markdown headings). The release is created only if all six builds succeed. The notes are the tag's message, then GitHub's "Full Changelog" link.
4. Once `releases/download/vX.Y.Z/SHA256SUMS` exists: `cargo publish`, then `cargo clean -p tuitube` (publish check-builds the packaged copy in `target/package/` into the shared `target/`, which can leave later builds tracking that copy).

## Security

Everything from YouTube is untrusted: titles, channel names, descriptions, feed XML, yt-dlp's JSON (it relays YouTube), image bytes, URLs.
- Ids are checked once where they come in (`ids::VideoId`, 11 of `[A-Za-z0-9_-]`; `ids::ChannelId`, `UC` + 22), and every URL tuitube opens, fetches or hands to a program is built from one (`VideoId::url`, `ChannelId::feed_url`…). A video id can start with `-`: programs get URLs, never bare ids, and always after `--`.
- Text that is shown goes through `video::one_line` (`text::clean`, whitespace collapsed, length capped: `MAX_TITLE`, `MAX_CHANNEL`, `MAX_DESCRIPTION`) when it's parsed (feed, yt-dlp, Takeout), before it's stored. Error text from yt-dlp goes through `ytdlp::error_line`, paths through `config::shown`, panic messages through `text::clean`.
- Nothing private goes on a command line: every user of the computer can read them (`ps`, `/proc/*/cmdline`). yt-dlp gets its URL or search on stdin (`--batch-file -`); mpv starts idle and gets the title, user agent, start and URLs over its socket (`player::commands`, JSON built with `serde_json`, so a title can't break out). Only Windows (no socket yet, and command lines aren't readable by other users there) passes them as mpv arguments.
- yt-dlp (`ytdlp.rs`) runs per request with `env_clear()` + `tools::child_env` (no `PYTHONPATH`, `LD_PRELOAD`, user site-packages or plugins; the certificate variables kept, and the proxy chosen at start), `current_dir` = `work/`, `--ignore-config --no-plugin-dirs --no-mark-watched --no-cookies --no-cookies-from-browser --no-remote-components`, `--no-js-runtimes` and only Deno named by path, its own `--cache-dir`, a timeout, capped output (`try_join!`: too much ends the run at once), its own process group, killed as a whole when a run ends before yt-dlp was waited for (`ytdlp::Run`: timeout, too much output, the request dropped on quit), so the Deno running YouTube's player script can't outlive it, and an `RLIMIT_CPU` (`MAX_CPU_SECONDS`) that it and Deno inherit as a backstop for when tuitube is gone. Its JSON is parsed leniently (every field optional; `ytdlp::lenient` skips list items that don't fit; dates outside 1970–2100 dropped). Never use `--exec`, `--netrc-cmd`, external downloaders, `--cookies-from-browser`, or let tuitube run `yt-dlp -U`.
- Stream URLs from yt-dlp must pass `ytdlp::stream_url_allowed` (https, `*.googlevideo.com` / `*.youtube.com`) before mpv sees them; image URLs must pass `ids::image_url_allowed` (https, `i.ytimg.com`, `iN.ytimg.com`, `yt3.googleusercontent.com`, `yt3.ggpht.com`) before they're fetched.
- mpv (`player.rs`) starts with `--no-config --load-scripts=no --terminal=no --ytdl=no --tls-verify=yes --idle=once` (mpv's own default accepts any certificate), the same cleaned environment, and is controlled over one end of a `socketpair` passed as fd 3 (`--input-ipc-client=fd://3`): no socket file exists, and mpv quits when tuitube's end closes. The title goes in with `$` doubled (`title` expands `${…}`), the user agent on one line, the sound added with `change-list audio-files append` (one item, never split). mpv's IPC can run programs; never expose it on a path, port or named pipe others can reach. `player::own` holds the process: asked to stop, mpv gets `QUIT_GRACE` and is then killed through its handle (never by process id). Windows has no IPC yet (mpv is only started and stopped).
- SponsorBlock (`sponsorblock.rs`) is opt-in (`sponsorblock = false` by default; turned on and off in the settings tab, `O`), since it tells a third party what you play. When on, each playback sends sponsor.ajay.app only the first 4 hex characters of the id's SHA-256 (`hash_prefix`), with categories from tuitube's own `CATEGORIES` list (names in settings are matched against it, unknown ones reported at start), never the id; the answer (every video in that bucket) is capped at `MAX_BYTES`, read leniently, filtered to the id asked about, `actionType` skip, sane finite times, at most `MAX_SEGMENTS`. Shown category names are tuitube's, never the server's. Its client (`feed::client_without_redirects`) follows no redirect. Only asked when mpv can be seeked (Unix) and the video isn't live.
- Nothing tells YouTube what you watched: yt-dlp always gets `--no-mark-watched`, mpv plays only the resolved streams, and a video is resolved only on Enter / `a` / `N`, or by autoplay when the one before it played to its end, never when a card is highlighted. `m` asks for the selected video's Mix; for a video with none, yt-dlp reads the video itself, the same request as playing it. Local history (`history = true` in settings) stays in `tuitube.db`.
- HTTP (`feed::client()`): rustls with ring, https only, no cookies, no `Referer`, timeouts, and redirects only to where a request could have gone (`feed::allowed_url`: YouTube's image hosts and its feeds), at most 2, so a redirect can't reach this computer, the network or plain http. A 429 from the feeds (`feed::TooManyRequests`) pauses feeds for `SLOW_DOWN`; a bot check or 429 from yt-dlp pauses background channel looks the same way (`app::slowed_down`, matching whole phrases, not a bare `429` that a channel id can hold), each time it comes, not just the first (an expired pause is cleared in `look_up_channel`).
- Proxy (`proxy.rs`): one, chosen at start from the first set of `proxy::NAMES` (`https_proxy`, `HTTPS_PROXY`, `all_proxy`, `ALL_PROXY`, `http_proxy`, `HTTP_PROXY`), for everything: reqwest gets it explicitly (never its own reading of the environment), and children get it under every one of those names (`tools::child_env`), since reqwest, yt-dlp and mpv/FFmpeg each read them differently and would otherwise take different routes. It must be `http://` (mpv can't use another kind and would go around it), else tuitube won't start; the error names the variable, never its value (it may hold a password). With none, reqwest uses no proxy and yt-dlp gets `--proxy ""` (not the system settings, which tuitube and mpv don't read). A chosen proxy never goes on a command line.
- Images: at most `MAX_BYTES`, cached by checked id only (`images::cache_name`), written under a fresh name (`create_new`) only after they decoded, a cached one that no longer decodes deleted, the cache pruned after `CACHE_FOR`; decoded only if the format is JPEG, PNG or WebP (`images::decode`; arboard is built without its TIFF/BMP), within `images::limits` (2048 px, 64 MB) and, for WebP, only after every frame header was checked against its canvas and 2048 px (`images::check_webp`: the decoder sizes its buffers from the frame, not the canvas `limits` sees), at most `MAX_BUILDING` decoding at once (a semaphore), a decoder panic contained (`images::panic_is_contained`, checked by the panic hook). Sixel/iTerm2 images aren't drawn under popups or under text (`Images::paints_over`).
- Image protocol (`images::picker`): what the terminal answers, unless `images` in settings / `TT_IMAGES` forces one; a terminal that answers nothing but whose environment says Ghostty or kitty gets the kitty protocol with the cell size from `TIOCGWINSZ` (`images::choose`). Thumbnails come from `VideoId::large_thumbnail_url` (1280×720 WebP), falling back to the search's URL and the 480×360 JPEG; channel photos are looked up only when real images can be drawn. `tuitube --check` prints the tools found and the image detection.
- Links open only with a URL built from a checked id (`app::open_url`: `open` on macOS/Windows, `xdg-open` found as an absolute path elsewhere, run in the home folder in its own process group, with only absolute `PATH` folders); `y` copies the same URL (arboard, kept for the run, or OSC 52 through the terminal). No link from a description or title is ever opened; `o` does nothing in `--demo`. The opener does get the URL on its command line, the one exception to the rule above: browsers take URLs no other way.
- tmux (`tmux.rs`): building the image `Picker` runs `tmux set -p allow-passthrough on` whenever TERM/TERM_PROGRAM says tmux, whatever `images` is. `tmux::save` reads the pane's own value first (the pane named by `TMUX`/`TMUX_PANE`, tmux found by absolute path, `-S` the socket) and `tmux::restore` puts it back on exit, after `--check`, after `--demo` and in the panic hooks.
- Pastes: only `Event::Paste` (bracketed paste) is pasted text, but on Windows, and from terminals that don't bracket pastes, a paste comes as keystrokes. `App::run` reads every event already waiting along with the first (`crossterm::event::poll(ZERO)`, never the stream, whose wake task would be lost), and `App::on_terminal_events` treats a run of different keys as a paste: added as text in an open box (submitted only if plain text ending in one Enter), ignored with no box open (`PASTED_KEYS`). One key held down acts as usual.
- SIGHUP (the terminal window closed) and SIGTERM quit the normal way (`AppEvent::Quit`), so the database is closed and yt-dlp runs end with what they started.
- Takeout import (`takeout.rs`): opened non-blocking and read only if it's a plain file (not a pipe or `/dev/zero`), at most 8 MB and `MAX_CHANNELS`, rows read by position (the header is localized), a row counts only if its id is a channel id, saved in one transaction; `\\server\share` paths are refused, and on Windows any path that starts with a separator (`config::maybe_remote`: the NT spelling `\??\UNC\server\…` reaches the network too). A channel's feed renames it (`Store::rename`), so a name in a Takeout file can't stick.
- Stored text is cleaned again when it's read (`store::video_row`), dates from the store go through saturating arithmetic, and `secure_delete` is on; under WAL that holds only after a checkpoint, so taking a video off History or Watch later checkpoints at once (`Store::scrub`, `wal_checkpoint(TRUNCATE)`). Saving where you are in a video only updates a History row that's still there (`Store::update_watch`): x on the video playing stays done. Videos older than `KEEP_VIDEOS` and in neither list are pruned at start.
- A channel's page is looked at in the background at most `MAX_LOOKUPS_PER_CHANNEL` times a session, and a live stream or premiere (whose date may be ahead of now) only by the `LIVE_EVERY` clock, so no video can keep yt-dlp busy.
- `settings.toml` names tuitube doesn't know are reported at start (`Settings::load_checked`), so a typo in a privacy setting isn't silently ignored. `A` and the settings tab change only their own key in the file as it is now (`Settings::save_one`), so a `history = false` or `sponsorblock = false` written meanwhile (by hand, or another tuitube) isn't undone, and is applied to the running session too.

## Architecture

**Event loop (`app.rs`, `App::run`).** One `tokio::select!` over terminal events, `AppEvent`s (feeds, yt-dlp answers, channel photos, resolved streams, mpv events, finished images) and a 1 s tick. Terminal events already waiting are read together (see Pastes, above); SIGHUP/SIGTERM become `AppEvent::Quit`. Each wake drains the backlog, then redraws; after each frame `Images::fetch` starts what the frame wanted. All state lives in `App`. Requests that change the view carry `App.request`, and answers to older ones are dropped; mpv events carry the playback number (`Player.play`).

**Views.** `View::{Home, Shorts, Search, WatchLater, History, Channel, Mix}`; `App::reload` rebuilds `App.videos` from the store (or the last search's results, or `App.mixes`) and keeps the selection by id. `App::show` switches views (pushing the old one on `back` for Backspace / Ctrl-o). Moving in the sidebar shows what's stored at once; Enter on a channel also fetches its newest 60 videos with yt-dlp. Search asks for 30 results, then 30 more when the selection nears the end (`App::load_more`), up to 150. `m` opens a video's Mix (`VideoId::mix_url`, `RD` + the id; `YtDlp::mix`, capped at `MIX_SIZE` since yt-dlp would page through over a thousand, repeats dropped); logged out, YouTube makes one only for music videos, and for others yt-dlp returns the bare video, which `ytdlp::mix_videos` reports as no Mix.

**Feeds (`feed.rs`).** Each subscription's Atom feed (15 newest uploads; `/shorts/` links mark Shorts), `PARALLEL` at once, `TRIES` tries with backoff (YouTube's feed server fails a lot). A channel's feed is fetched again only when its stored copy is older than `refresh_minutes` (default 30, at least 15, `Settings::refresh_every`), checked every `CHECK_EVERY`; `R` fetches every feed now; Home's header says when feeds were last updated (`App.feeds_updated`). A failed feed waits for the next check (`App.refreshed`). A feed missing (404) on every try (`feed::NotFound`) gets one background yt-dlp look per session (`App.gone_checks`); if yt-dlp says the channel was removed, doesn't exist or was terminated (`app::channel_gone`), it's marked gone (`channels.gone`, `Store::set_gone`): its feed isn't fetched again until you subscribe to it again (x then S or u), and the sidebar dims and marks it for you to unsubscribe (tuitube never unsubscribes for you). Feeds carry no lengths: `App::want_length` (called for each card on screen without one) has yt-dlp list the channel's Videos tab, then its Live tab (`ytdlp::Tab`), 30 videos per look for the cost of one; when each tab was looked at is kept in `channels.videos_checked` / `streams_checked` (`Store::tab_checked`), so a tab is looked at again only for a video newer than that, or every `LIVE_EVERY` for a live stream or premiere on screen. Opening a channel fetches its videos only when the kept ones are older than `refresh_minutes`.

**Store (`store.rs`).** SQLite: `channels` (subscribed flag, photo URL and when it was looked up, when the feed was fetched), `videos` (merged across sources: a later source keeps what an earlier one knew), `watch_later`, `history` (position and length, for resuming and the red watched bar).

**Channel photos.** `App::avatar_url`: from the store if looked up in the last `AVATAR_EVERY`, else the same background look at the channel's Videos tab as for lengths (`App::look_up_channel`, its own semaphore, so it never delays what you asked for); asked for at 176 px (`ytdlp::small_avatar`).

**Playing.** Enter / `a` → `YtDlp::resolve` (format from `ytdlp::Quality`: no AV1, at most `max_height`) → `Player::start`. Resumes from the stored position if it's more than `RESUME_AFTER` from either end; the position is saved every `SAVE_EVERY` and when playback ends. The player bar (`ui::player_bar`) is a box: the title and channel in its border (and "Next: …" on the right of it when autoplay will play it and the title leaves `MIN_NEXT` columns), and inside the position, a bar across with a dot, the length and the keys with icons (`N` only when something is up next; `⟳ A` lit while autoplay is on), the keys dropped first in a narrow window. Autoplay: playing a card sets `App.up_next` to the cards after it (or, once a Mix of the video playing loads, the rest of the Mix); mpv's `end-file` with reason `eof` (`PlayerEventKind::Ended`) marks the playback ended, and when mpv then exits within `ENDED_WITHIN` of the end with `autoplay` on (`A`), the next one plays, unless a video you chose is still loading. Closing mpv's window or `X` never moves on; a video autoplay can't play is skipped, `MAX_SKIPS` in a row at most, and a bot check stops it. Windows has no mpv events, so no autoplay there (`N` works). Resolving has its own counter (`App.resolves`), so starting a video never drops a view's answer. SponsorBlock: once mpv starts, `App::look_up_segments` asks for the video's segments (`AppEvent::Segments`, carrying the playback number); on each `time-pos`, `Skipper::due` returns a segment playback is inside and hasn't skipped yet, run on through the ones that touch it (each left alone if marked on a video whose length differs by more than `LENGTH_SLACK`), and `Player::seek_to` seeks to its end (`absolute+exact`). Each is skipped once, so seeking back into one plays it. The player bar's title row says `[SKIP] <category> · <length>` in the theme's yellow (`warning`) for `SKIP_SHOWN_FOR`, where "Next: …" goes.

**UI (`ui/`).** Laid out as tuigram's panes: round-bordered boxes (`ui::bordered`), the one with the keys in the accent color (`ui::border`). `mod.rs`: the search box (`search_box`, drawn as the videos' box's title, lined up with the thumbnails), player bar, status bar (key hints written with the keys in backticks, as tuigram's: `hint_spans` shows the keys in the accent color, `hints_fitting` drops whole hints from the end), and the `?` popup (`App.help`, a `HelpMenu`): a Keys tab and a Settings tab (`O` opens it there) of checkboxes (Shorts, live streams, descriptions, autoplay, SponsorBlock, history) and the built-in themes; Enter saves the row at once (`App::change_setting`). `shorts = false` drops Shorts from the sidebar (`App::menu`) and `Settings::hides` keeps Shorts and live/upcoming videos out of every view but Watch later and History. `sidebar.rs`: a box with the logo in its border, the menu, then under a rule (`├─ Subscriptions ─┤`) the subscriptions, scrolled to the selection. `grid.rs`: a box with the search box in its border (and the feeds' progress on its right when the header doesn't say it), the header, then the cards a column in from the border; `geometry` fits cards of at least `card_width` columns, thumbnails 16:9 in pixels from the terminal's cell size, and the top of the next row in what's left (kitty and block images are cut with `allow_clipping`; sixel/iTerm2 ones show a placeholder there); a card is the thumbnail (with the length badge), then on a shade of its own (the theme's `surface`, `Colors.selected`, a column of padding each side and a blank row closing it) the watched bar, the channel photo (or its initial) beside a two-line title, the channel, views · age, and the description's start. Below 70 columns the sidebar and the grid take turns (the grid while the search box is open).

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

tuitube: a terminal YouTube client for one person's own use, with a YouTube-like layout (sidebar + grid of video cards) and both arrow keys and vim keys. Rust, ratatui, tokio, MIT. A sibling of tuigram (`../tuigram`, Telegram) and tuimeta (`../tuimeta`, Meta's messengers): same security posture, same themes, same `text::clean`, config and settings code. The research behind every design choice is `reports/YouTube terminal client.md` (notes in `research_notes/`); read its security section before changing how programs are started or what is sent to YouTube.

No Google account, ever, in this version: subscriptions are local (imported from Google Takeout's `subscriptions.csv`), refreshed from public channel RSS feeds. Don't add cookie login or `--cookies-from-browser`: Google cookies are the whole Google account (Gmail, Drive), and YouTube's terms let it suspend the account. tuitube contains none of YouTube's cipher or InnerTube code; yt-dlp (a separate program) does that.

## Running

Running tuitube is safe (no account), but it talks to YouTube and mpv opens windows and plays sound. For checks, prefer tests that render into ratatui's `TestBackend` (`ui/mod.rs` tests). Use a separate data folder for trying things: `TT_DATA_DIR=$HOME/tt-test cargo run` (a full path in your own home: `/tmp` is shared, and relative paths are refused). `tuitube --demo` (`demo.rs`) fills the real UI with made-up channels and videos, preloaded pictures drawn in code, an in-memory store and `App.demo` set: nothing is fetched or played. `docs/hero.png` is one frame of it: `cargo test -- --ignored export_hero_screen` writes `target/hero/screen.json` (cells, colors, where `Images::placed` says each picture went), and `tools/hero.py` draws it as Ghostty would (JetBrains Mono, Nerd Font icons, box lines drawn to the cell edges). CI runs the tests on Windows too, where tuitube can't control mpv yet (`Player::controllable` is false: no pause, seek or place saved, only `X`, `A` and `r` in the player bar, no SponsorBlock). A test never takes that from the system running it: a player with no mpv behind it (`show_playing`) is controllable in tests on every system, and a test of Windows' side says so with `app::tests::mpv_control(app, false)`, checking both. Don't branch a test on `cfg!(unix)` for what mpv can do: 0.2.0, 0.3.0 and 0.4.0 each failed Windows CI that way, passing on the Mac. Tests that talk to YouTube, sponsor.ajay.app or run mpv are `#[ignore]`d: `cargo test -- --ignored live` (logged out, a handful of requests; the mpv ones play generated silence; the MPRIS one needs a session D-Bus, so Linux: in a container, `dbus-run-session -- cargo test -- --ignored live_mpris`, and run tuitube there under `script` with `timeout --foreground`, since plain `timeout` puts it in a background process group that SIGTTOU stops at `enable_raw_mode`).

## Commands

```sh
cargo build
cargo test                       # offline tests
cargo test -- --ignored live     # against YouTube, sponsor.ajay.app and the real mpv
cargo clippy --all-targets       # keep it warning-free
cargo fmt
cargo run -- --import path/to/subscriptions.csv
```

Needs `yt-dlp`, `deno` and `mpv` at run time (`brew install yt-dlp mpv`: Homebrew's yt-dlp depends on Deno). `tools::Tools::find` resolves each to an absolute path once (settings `yt_dlp`/`mpv`/`deno`, `TT_YT_DLP`/`TT_MPV`/`TT_DENO`, else absolute `PATH` entries, then Homebrew/system folders); a program is never started by bare name. `main` (a plain `fn`, before the tokio runtime or any thread) also cuts tuitube's own `PATH` down to its absolute entries (`tools::absolute_path_entries`), because code it uses starts programs by name (ratatui-image's `tmux`, crossterm's `tput`, xdg-open's helpers): none can come from the folder tuitube was started in. `.env` is read only by development builds, only from the source folder (`CARGO_MANIFEST_DIR`, never the working directory: some `TT_*` keys name programs to run) and only `TT_*` keys (`config::load_dotenv`, never the process environment). The data dir (`TT_DATA_DIR`, a full path, or the platform app-data dir; `tuitube --help` prints it) is made by `config::make_private_dir`: the folders above it checked first (`private_place`: changeable only by you or root, owners compared with `geteuid`), then the folder made 0700 or found to be a real folder of yours (never a link), set 0700, and on macOS cleared of inherited ACLs (`/bin/chmod -RN`); on Windows a `TT_DATA_DIR` must be in the user profile. It holds `tuitube.db` (SQLite, 0600), `settings.toml` (0600, written through a rename of a per-process temp file), `cache/images`, `cache/yt-dlp`, `work/` (yt-dlp's working directory) and, on macOS, `player/` (mpv's copy in `tuitube.app`, `bundle.rs`).

## Releasing

Release binaries are built only by `.github/workflows/release.yml` (pushing a `v*` tag): six targets (Linux on Ubuntu 22.04 for a glibc 2.35 floor, macOS, Windows with a static C runtime; x86_64 and ARM64 each), tests run on the native ones, then the GitHub release gets the archives, `SHA256SUMS` and a provenance attestation covering both. `cargo binstall tuitube` takes those archives (`[package.metadata.binstall]` in `Cargo.toml`), so asset names and the `v<version>` tag must stay as `pkg-url` expects, and the release must be up before `cargo publish`. `.github/workflows/ci.yml` runs fmt, clippy (`-D warnings`) and tests on Linux, macOS and Windows for every push, and `cargo audit` weekly.

1. Push the work being released and wait for CI to pass on all three systems before bumping the version (Windows fails what a Mac passes; see Running). Then bump `version` in `Cargo.toml`, run `cargo build` (updates `Cargo.lock`), then tests, clippy, `cargo fmt --check` and `actionlint`.
2. Commit and push `main`; wait for CI.
3. Write a short changelog (a few bullets, for users) to a file outside the repo, then `git tag -a vX.Y.Z --cleanup=whitespace -F <file> && git push origin vX.Y.Z` (without `--cleanup`, git drops `#` lines such as Markdown headings). The release is created only if all six builds succeed. The notes are the tag's message, then GitHub's "Full Changelog" link.
4. Once `releases/download/vX.Y.Z/SHA256SUMS` exists: `cargo publish`, then `cargo clean -p tuitube` (publish check-builds the packaged copy in `target/package/` into the shared `target/`, which can leave later builds tracking that copy).

## Security

Everything from YouTube is untrusted: titles, channel names, descriptions, feed XML, yt-dlp's JSON (it relays YouTube), image bytes, URLs.
- Ids are checked once where they come in (`ids::VideoId`, 11 of `[A-Za-z0-9_-]`; `ids::ChannelId`, `UC` + 22; `ids::PlaylistId`, 13–64; `ids::ChannelName`, a handle of 3–30 `[A-Za-z0-9._-]`), links pasted in only through `links::parse` (YouTube's hosts, ids kept, the link itself never used), and every URL tuitube opens, fetches or hands to a program is built from one (`VideoId::url`, `ChannelId::feed_url`…). A video id can start with `-`: programs get URLs, never bare ids, and always after `--`.
- Text that is shown goes through `video::one_line` (`text::clean`, whitespace collapsed, length capped: `MAX_TITLE`, `MAX_CHANNEL`, `MAX_CHAPTER`) when it's parsed (feed, yt-dlp, Takeout), before it's stored; descriptions and comments, shown on their lines, through `video::lines` (each line so, a blank line kept between paragraphs, `MAX_DESCRIPTION` / `MAX_COMMENT` characters, `MAX_LINES` lines), and cards show a description through `one_line`. A stored description gives way only to a longer one (a search's snippet never replaces a feed's whole text). Chapters are also kept only with a finite start inside the video, in order, at most `chapters::MAX_CHAPTERS` (`chapters::tidy`). Error text from yt-dlp goes through `ytdlp::error_line` (which also drops yt-dlp's advice for its own command line: cookies, `-t sleep`, `yt-dlp -U`), paths through `config::shown`, panic messages through `text::clean`.
- Nothing private goes on a command line: every user of the computer can read them (`ps`, `/proc/*/cmdline`). yt-dlp gets its URL or search on stdin (`--batch-file -`); mpv starts idle and gets the title, user agent, start and URLs over its socket (`player::commands`, JSON built with `serde_json`, so a title can't break out), and the chapters the same way (`Player::set_chapters`, `set_property chapter-list`). Only Windows (no socket yet, and command lines aren't readable by other users there) passes them as mpv arguments.
- yt-dlp (`ytdlp.rs`) runs per request with `env_clear()` + `tools::child_env` (no `PYTHONPATH`, `LD_PRELOAD`, user site-packages or plugins; the certificate variables kept, and the proxy chosen at start), `current_dir` = `work/`, `--ignore-config --no-plugin-dirs --no-mark-watched --no-cookies --no-cookies-from-browser --no-remote-components`, `--no-js-runtimes` and only Deno named by path, its own `--cache-dir`, a timeout, capped output (`try_join!`: too much ends the run at once), its own process group, killed as a whole when a run ends before yt-dlp was waited for (`ytdlp::Run`: timeout, too much output, the request dropped on quit), so the Deno running YouTube's player script can't outlive it, and an `RLIMIT_CPU` (`MAX_CPU_SECONDS`) that it and Deno inherit as a backstop for when tuitube is gone. Its JSON is parsed leniently (every field optional; `ytdlp::lenient` skips list items that don't fit, and takes anything else where a list goes as an empty one; dates outside 1970–2100 dropped). Never use `--exec`, `--netrc-cmd`, external downloaders, `--cookies-from-browser`, or let tuitube run `yt-dlp -U`.
- Stream URLs from yt-dlp must pass `ytdlp::stream_url_allowed` (https, `*.googlevideo.com` / `*.youtube.com`) before mpv sees them; image URLs must pass `ids::image_url_allowed` (https, `i.ytimg.com`, `iN.ytimg.com`, `yt3.googleusercontent.com`, `yt3.ggpht.com`) before they're fetched.
- Subtitles: WebVTT URLs from the same resolve answer (`ytdlp::captions`, read from any JSON so odd subtitles never stop a video, `live_chat` left out, each URL through `stream_url_allowed`, at most `MAX_CAPTIONS`), one track picked per playback (`ytdlp::pick_caption`: the uploader's in your language, then YouTube's captions as spoken, `-orig`, then translated), given to mpv as one item of `sub-files` over the socket (`--sub-file=` on Windows) with `sub-visibility` from `subtitles`; `T` sets it on the video playing (`Player::show_subtitles`). Languages: `subtitle_languages`, else the system locale and English (`Settings::subtitle_languages`), only names shaped like language codes.
- mpv (`player.rs`) starts with `--no-config --load-scripts=no --terminal=no --ytdl=no --tls-verify=yes --idle=once` (mpv's own default accepts any certificate), the same cleaned environment, and is controlled over one end of a `socketpair` passed as fd 3 (`--input-ipc-client=fd://3`): no socket file exists, and mpv quits when tuitube's end closes. The title goes in with `$` doubled (`title` expands `${…}`), the user agent on one line, the sound added with `change-list audio-files append` (one item, never split). mpv's IPC can run programs; never expose it on a path, port or named pipe others can reach. `player::own` holds the process: asked to stop, mpv gets `QUIT_GRACE` and is then killed through its handle (never by process id). Windows has no IPC yet (mpv is only started and stopped). Where tuitube fills in Now Playing (`player::NOW_PLAYING`, macOS), the video loads as an EDL with the channel as its `artist` tag (`player::file_to_load`), since mpv's Now Playing takes the artist only from the file's tags: the shape mpv's ytdl_hook gives YouTube streams (`edl://!no_clip;!no_chapters;!global_tags,artist=…;<url>;`), each text after `%n%`, its length in bytes, so nothing in it ends its field; not for a live stream. Measured on YouTube's streams to play, seek, resume (`start`), loop, filter and end as the bare URL. mpv opens no special protocol (`av://`) inside an EDL, so its live test plays a file mpv wrote first. Now and then YouTube refuses the stream addresses yt-dlp got (HTTP 403, the subtitles 429): mpv says `end-file` with reason `error` (`PlayerEventKind::Failed`) and quits. Before anything played, the video is resolved again once (`App::on_stream_failed`, `App.retried`, from where it was to start); a second refusal, or one after it played (addresses expire after about six hours), is said.
- On macOS mpv runs from `<data>/player/<key>/tuitube.app` (`bundle.rs`, `bundle::put_mpv_in` at start, and in `--check`), so notch apps show what plays: they read Now Playing (mpv publishes it, from `force-media-title`), and some (Vorssaint) skip a player with no app-bundle id, as a bare program has. The bundle holds a **copy** of the mpv found (macOS takes the bundle from the path that ran; signing a hard link would change Homebrew's file), signed ad hoc by `/usr/bin/codesign` so its signature names the bundle (`io.github.erictran308.tuitube`), and tried with `--version` (an mpv that loads its libraries from beside itself doesn't run copied). It's built under a temporary name and renamed into place, made again when the mpv found changes (`bundle::key`: its real path, size, time and the Info.plist), and other bundles pruned. Both programs run with an empty environment. If it can't be made, mpv runs as itself and the status bar says why. mpv's own bundle mode needs `MPVBUNDLE=true`, never in the cleaned environment.
- pepper-play (Pepper's player, inside Pepper.app; Pepper only, `pepper.rs`) runs as mpv does: the same options, the same cleaned environment plus `PEPPER_PORT` alone (never in `KEPT`, which yt-dlp and Deno get too), controlled over the same socketpair, stopped the same way. The token that ties a playback's picture to its box (16 bytes of `/dev/urandom`, `pepper::new_token`) goes to it only over the socket (`script-message-to main pepper-token`), and to Pepper only in tuitube's own escape sequence to its tab. Those sequences (`pepper::place`, `pepper::remove`) carry nothing but the token and cell numbers, are written only when `App.pepper` is set (`PEPPER_PORT`, not in a multiplexer: tmux, GNU screen or zellij, `pepper::MULTIPLEXERS`), and never by tests. Programs start one at a time (`tools::starting`), with the player's socketpair made under the same lock: macOS has no `SOCK_CLOEXEC`, so a program started by another thread between `socketpair` and std marking its ends close-on-exec would get the player's control socket. pepper-play is Pepper's, not tuitube's (`../pepper/pepper-play`): it loads libmpv (GPL), so it's a program of its own, and any app can drive it; tuitube finds it from the `pepper_play` setting, `TT_PEPPER_PLAY`, or `PEPPER_PLAY`, which Pepper gives every shell (`Tools::find_pepper_play`).
- Visualizer (`visualizer.rs`, drawn by `ui/visualizer.rs`; `visualizer = true`, shown by `App::visualizing` only while the sound alone plays and mpv can be controlled, or in `--demo`): tuitube never has the sound, so mpv's FFmpeg measures it. Once mpv says `playback-restart` (`PlayerEventKind::Restarted`), `Player::add_visualizer` sends `af add` of `visualizer::filter()`, built from tuitube's own constants only (`aformat` stereo, `asplit`, `pan` mono, a double `bandpass` per band (`BANDS`, 24: each costs mpv about 0.2% of a core, as `astats` reads every sample; no FFmpeg filter that joins two streams keeps the numbers, so they can't be measured at a lower rate), `amerge`, `astats` per channel, `pan` back to the sound's two channels), with `request_id` `FILTER_ADDED`. Never before the sound plays: a filter mpv can't make then stops the sound altogether; once it plays, mpv keeps its old chain and answers an error (`Visualizer(false)`: said once, `App.visualizer_failed`, not tried again that session). While the bars show and it isn't paused, the socket's writer task asks `get_property af-metadata/tuitube` every `visualizer::EVERY` (`Player::follow_spectrum`, `request_id` `SPECTRUM`); `visualizer::levels` reads only `lavfi.astats.<n>.RMS_level` (non-finite is silence, clamped to 0 dB). `Spectrum` holds each answer `LEAD` (mpv's `audio-buffer`) so the bars move with what's heard, and `ui::visualizer` draws them as bars a column wide with a column between, in the rainbow or, with `visualizer_white`, all in the theme's `text`; turned off, `af remove @tuitube`. Nothing is fetched or sent anywhere.
- MPRIS (`mpris.rs`, Linux only: `mpris::AVAILABLE`, the `mpris-server` crate on zbus with its `tokio` feature, a Linux-only dependency): mpv publishes nothing there, so tuitube answers on the session bus as `org.mpris.MediaPlayer2.tuitube` (`.instance<pid>` if another tuitube has it), connected at start within `CONNECT_WITHIN` and only with `now_playing` on; turned off, `App.mpris` is dropped and the name given up (turned on, `AppEvent::MprisStarted`). What it says is `mpris::Shown`, built by `App::now_shown` (the title as shown, DeArrow's too, the channel, `VideoId::url`, the length, the position, the cover as a `file://` URL of the JPEG `Images::cover` wrote, the volume, `can_seek` only where mpv can be told and not live) and sent once a wake (`App::tell_mpris`, next to `images.fetch`): `Mpris::update` says only the properties that changed, and `Seeked` for a jump (`SEEK_SLACK`), through one task so signals keep their order. What it's asked comes back as `AppEvent::Mpris` (`mpris::Ask`) and runs what the keys run (`App::on_mpris`): ⏭ ⏮ as `remote_next` / `remote_previous`, Stop as X, a seek clamped to the video, `SetPosition` only for the playback its track id names (`/io/github/erictran308/tuitube/play/<n>`) and inside the video, the volume only if finite. `OpenUri`, Raise, Quit, rate, shuffle and loop are refused (`NotSupported`/`Unsupported`); every property getter answers, or `GetAll` would fail for all. Only programs of your own user reach the session bus; zbus starts a program only when `DBUS_SESSION_BUS_ADDRESS` names one (`unixexec:`, or `ibus:`, which runs `ibus` by name, from `PATH`'s absolute folders); the environment is trusted, and its `launchctl` is macOS's launchd only. `tuitube --check` says whether it's on the bus.
- SponsorBlock (`sponsorblock.rs`) is opt-in (`sponsorblock = false` by default; turned on and off in the settings tab, `O`), since it tells a third party what you play. When on, each playback sends sponsor.ajay.app only the first 4 hex characters of the id's SHA-256 (`hash_prefix`), with categories from tuitube's own `CATEGORIES` list (names in settings are matched against it, unknown ones reported at start), never the id; the answer (every video in that bucket) is capped at `MAX_BYTES`, read leniently, filtered to the id asked about, `actionType` skip, sane finite times, at most `MAX_SEGMENTS`. Shown category names are tuitube's, never the server's. Its client (`feed::client_without_redirects`) follows no redirect. Only asked when mpv can be seeked (Unix) and the video isn't live.
- DeArrow (`dearrow.rs`) is opt-in the same way (`dearrow = false`; the settings tab, `:dearrow`). When on, each card drawn (`App::want_title`, from `grid.rs` and `list.rs`) is asked about once a session after the frame (`App::fetch_titles`, `dearrow::Titles`: `AT_ONCE` at a time, `MAX_ASKS` a session, stopped after `MAX_FAILURES` in a row until turned on again), sending sponsor.ajay.app/api/branding only `sponsorblock::hash_prefix`, through the same no-redirect client and capped read (`sponsorblock::fetch`). The answer is read leniently and filtered to the id asked about; its best title (locked, then votes) is kept only if locked or not voted down and not `original`, `‹` back to `<`, the formatter's `>` marks dropped, then `video::one_line`. It's only shown (`App::title`: cards, list rows, the player bar, the `i` popup with "On YouTube: …" under it, mpv's title): never stored, searched or matched against `blocked_words`. Thumbnails aren't asked for (they'd need the whole id, to another host).
- Comments (`YtDlp::comments`: `--write-comments`, `MAX_COMMENTS` top ones, no replies) are asked for only when the `i` popup's Comments tab opens, once a session per video: yt-dlp reads the video's page for them, the same request as playing it. A link in a description or comment is text; nothing opens it.
- Nothing tells YouTube what you watched: yt-dlp always gets `--no-mark-watched`, mpv plays only the resolved streams, and a video is resolved only on Enter / `a` / `N` (a link pasted in only shows its card), or by autoplay (or the Jukebox) when the one before it played to its end, never when a card is highlighted or put in the Jukebox (`e` / `E` only store it). `M` asks for the selected video's Mix; for a video with none, yt-dlp reads the video itself, the same request as playing it. Local history (`history = true` in settings) stays in `tuitube.db`.
- HTTP (`feed::client()`): rustls with ring, https only, no cookies, no `Referer`, timeouts, and redirects only to where a request could have gone (`feed::allowed_url`: YouTube's image hosts and its feeds), at most 2, so a redirect can't reach this computer, the network or plain http. A 429 from the feeds (`feed::TooManyRequests`) pauses feeds for `SLOW_DOWN` and calls the rest of the round off (its semaphore closed, as for an outage); a bot check or 429 from yt-dlp pauses background channel looks the same way (`app::slowed_down`, matching whole phrases, not a bare `429` that a channel id can hold), each time it comes, not just the first (an expired pause is cleared in `look_up_channel`).
- Proxy (`proxy.rs`): one, chosen at start from the first set of `proxy::NAMES` (`https_proxy`, `HTTPS_PROXY`, `all_proxy`, `ALL_PROXY`, `http_proxy`, `HTTP_PROXY`), for everything: reqwest gets it explicitly (never its own reading of the environment), and children get it under every one of those names (`tools::child_env`), since reqwest, yt-dlp and mpv/FFmpeg each read them differently and would otherwise take different routes. It must be `http://` (mpv can't use another kind and would go around it), else tuitube won't start; the error names the variable, never its value (it may hold a password). With none, reqwest uses no proxy and yt-dlp gets `--proxy ""` (not the system settings, which tuitube and mpv don't read). A chosen proxy never goes on a command line.
- Images: at most `MAX_BYTES`, cached by checked id only (`images::cache_name`), written under a fresh name (`create_new`) only after they decoded, a cached one that no longer decodes deleted, the cache pruned after `CACHE_FOR`; decoded only if the format is JPEG, PNG or WebP (`images::decode`; arboard is built without its TIFF/BMP), within `images::limits` (2048 px, 64 MB) and, for WebP, only after every frame header was checked against its canvas and 2048 px (`images::check_webp`: the decoder sizes its buffers from the frame, not the canvas `limits` sees), at most `MAX_BUILDING` decoding at once (a semaphore), a decoder panic contained (`images::panic_is_contained`, checked by the panic hook). Sixel/iTerm2 images aren't drawn under popups or under text (`Images::paints_over`). Text is measured as ratatui and the terminal draw it, a grapheme at a time (`ui::fit`, `ui::tail`, `ui::wrap`, card titles through `wrap`; `unicode-segmentation`): ⚔️ (with U+FE0F) is two columns though ⚔ is one, 👍🏽 two, not four. `ui::pin_emoji_widths` marks each U+FE0F emoji cell `ForcedWidth` after every frame: ratatui 0.30's diff otherwise also sends the column it covers, and its crossterm backend sends that without a cursor move, so a terminal that drew the emoji two wide (Ghostty) put it, and the rest of the row, a column right. Now Playing's picture (`Images::cover`, where mpv shows one: `player::NOW_PLAYING`, macOS) is the video's thumbnail, cached or fetched as a card's (same hosts, `MAX_BYTES`, `decode`, `contained`), cut square (`COVER_SIDE`) and written as a JPEG of tuitube's own (`cache/images/p-<id>.jpg`, `write_private`, pruned after `COVER_FOR`). Once made and mpv plays (`AppEvent::Cover`, `Playing::give_cover` on `Restarted`), it goes to mpv as `video-add` with `flags` `auto` and `albumart` (`player::cover_command`, absolute paths only): listed, never selected, so the video stays on screen; mpv's Now Playing takes the first image track's `external-filename`. Never a URL there: mpv's Swift would fetch it itself (`NSImage(contentsOf:)`). All of Now Playing goes with `now_playing` (on by default; the settings tab, `:now-playing`), since any app that reads Now Playing sees the title: off, mpv starts with `--input-media-keys=no` (`--media-controls=no` does nothing on macOS) and gets no picture or channel; switched while playing, `Player::set_now_playing` sets it over the socket and macOS drops or takes mpv at once (measured: mpv's own info keeps updating, but without its controls it isn't eligible). The live mpv tests run with it off, so they don't take over the notch.
- Image protocol (`images::picker`): what the terminal answers, unless `images` in settings / `TT_IMAGES` forces one; a terminal that answers nothing but whose environment says Ghostty or kitty gets the kitty protocol with the cell size from `TIOCGWINSZ` (`images::choose`). Thumbnails come from `VideoId::large_thumbnail_url` (1280×720 WebP), falling back to the search's URL and the 480×360 JPEG; channel photos are looked up only when real images can be drawn. `tuitube --check` prints the tools found and the image detection.
- Links open only with a URL built from a checked id (`app::open_url`: `open` on macOS/Windows, `xdg-open` found as an absolute path elsewhere, run in the home folder in its own process group, with only absolute `PATH` folders); `y` copies the same URL (arboard, kept for the run, or OSC 52 through the terminal). No link from a description or title is ever opened; `o` does nothing in `--demo`. The opener does get the URL on its command line, the one exception to the rule above: browsers take URLs no other way.
- tmux (`tmux.rs`): building the image `Picker` runs `tmux set -p allow-passthrough on` whenever TERM/TERM_PROGRAM says tmux, whatever `images` is. `tmux::save` reads the pane's own value first (the pane named by `TMUX`/`TMUX_PANE`, tmux found by absolute path, `-S` the socket) and `tmux::restore` puts it back on exit, after `--check`, after `--demo` and in the panic hook (`screen.rs`).
- The command line (`commands.rs`): typed text is only ever matched against tuitube's own command table and values, never run or passed to a program; times go to mpv as JSON numbers. A paste goes on the line and never runs it (no Enter is taken from a paste there). File completion for `import` lists only the folder typed, never one `config::maybe_remote` flags, reads at most `MAX_READ` entries once per folder a session, doesn't follow links (one is offered only if it's named `*.csv`), and leaves out names with characters that don't show (`text::is_hidden`, controls), so a name can't show or complete as something else.
- Pastes: only `Event::Paste` (bracketed paste) is pasted text, but on Windows, and from terminals that don't bracket pastes, a paste comes as keystrokes. `App::run` reads every event already waiting along with the first (`crossterm::event::poll(ZERO)`, never the stream, whose wake task would be lost), and `App::on_terminal_events` treats a run of different keys as a paste: added as text in an open box (submitted only if plain text ending in one Enter), ignored with no box open (`PASTED_KEYS`). One key held down acts as usual. A run in an open box holding a key that edits (Backspace, an arrow, Ctrl-w, Esc) is no paste: it's typing come all at once (a slow link), run key by key, Enter only as the last and never on the command line, and nothing once the box closes (`App::takes_text`). The boxes edit their line with one function (`app::edit_line`: Backspace or Ctrl-h, Ctrl-u, Ctrl-w, `text::is_hidden` characters refused, a length cap).
- SIGHUP (the terminal window closed) and SIGTERM quit the normal way (`AppEvent::Quit`), so the database is closed, yt-dlp runs end with what they started, and where you are in a video and the volume are saved. The terminal (`screen.rs`) is taken over and handed back by tuitube's own code, not `ratatui::init`/`restore`, which print failures with `eprintln!` (a panic when stderr is a closed tab; one in the panic hook aborts). A closed tab's terminal fails every write with EIO, even of nothing, though `isatty` may still say yes (`screen::gone`): then nothing is put back, and stdout, and stderr if it was that terminal, go to /dev/null, so what's written on the way out can't fail. No frame is drawn once quitting, and a frame that fails because the tab is gone is a quit too.
- Takeout import (`takeout.rs`): a file, or a folder searched `MAX_DEPTH` down (`MAX_ENTRIES` entries, links not followed, on a blocking thread: `App::import` → `AppEvent::Imported`), each file recognized by what's in it since Takeout's names are localized (`Takeout`: subscriptions, a playlist's `<name>-videos.csv`, Watch later by its name in `WATCH_LATER`'s languages, `watch-history.json`; a history `.html` only says to export JSON). Each is opened non-blocking and read only if it's a plain file (not a pipe or `/dev/zero`), at most 8 MB (`MAX_HISTORY_BYTES` for history) and `MAX_CHANNELS` / `MAX_PLAYLIST` / `MAX_HISTORY`, rows read by position (the header is localized). A row counts only if its id checks out and it has the file's shape: a subscription has the channel's URL second, or three columns (your own `channel.csv` has more), a playlist row an id and a time (your uploads' `videos.csv` has more). History drops ads (`details`) and YouTube Music, keeps each video's last watch, and a title only after the English "Watched " (other languages' are looked up). Saved in one transaction each (`takeout::save`), history only with `history = true`; a video already known keeps what it has (`Store::save_if_unknown`); a video known only by its id is a `Video::placeholder` (title `youtu.be/<id>`, `needs_details`), and the cards on screen are asked about after the frame (`App::want_details`, `App::fetch_details`: one look of `MAX_DETAILS` at a time through `YtDlp::details`, YouTube's `watch_videos` list, a flat listing that asks for no video to play; `MAX_DETAIL_LOOKS` a session). `\\server\share` paths are refused, and on Windows any path that starts with a separator (`config::maybe_remote`: the NT spelling `\??\UNC\server\…` reaches the network too). A channel's feed renames it (`Store::rename`), so a name in a Takeout file can't stick.
- Stored text is cleaned again when it's read (`store::video_row`), dates from the store go through saturating arithmetic, and `secure_delete` is on; under WAL that holds only after a checkpoint, so taking a video off History, Watch later or the Jukebox checkpoints at once (`Store::scrub`, `wal_checkpoint(TRUNCATE)`). Saving where you are in a video only updates a History row that's still there (`Store::update_watch`): x on the video playing stays done. Videos older than `KEEP_VIDEOS` and in none of the lists are pruned at start.
- A channel's page is looked at in the background at most `MAX_LOOKUPS_PER_CHANNEL` times a session, and a live stream or premiere (whose date may be ahead of now) only by the `LIVE_EVERY` clock, so no video can keep yt-dlp busy.
- `settings.toml` names tuitube doesn't know are reported at start (`Settings::load_checked`), so a typo in a privacy setting isn't silently ignored. `A` and the settings tab change only their own key in the file as it is now (`Settings::save_one`), so a `history = false`, `sponsorblock = false`, `dearrow = false` or `now_playing = false` written meanwhile (by hand, or another tuitube) isn't undone, and is applied to the running session too (the volume, saved on the tick after it changes, applies them too).

## Architecture

**Event loop (`app.rs`, `App::run`).** One `tokio::select!` over terminal events, `AppEvent`s (feeds, yt-dlp answers, channel photos, resolved streams, mpv events, finished images) and a 1 s tick. Terminal events already waiting are read together (see Pastes, above); SIGHUP/SIGTERM become `AppEvent::Quit`. Each wake drains the backlog, then redraws; after each frame `Images::fetch` starts what the frame wanted. All state lives in `App`. Requests that change the view carry `App.request`, and answers to older ones are dropped; mpv events carry the playback number (`Player.play`).

**Views.** `View::{Home, Shorts, Search, Jukebox, WatchLater, History, Channel, Mix, Link, Playlist, MyPlaylist, Group}`; `App::reload` rebuilds `App.videos` from the store (or the last search's results, `App.mixes`, or `App.jukebox`) and keeps the selection by id. `App::show` switches views (pushing the old one on `back` for Backspace / Ctrl-o). Moving in the sidebar shows what's stored at once; Enter on a channel also fetches its newest 60 videos with yt-dlp. Search asks for 30 results, then 30 more when the selection nears the end (`App::load_more`), up to 150. `M` opens a video's Mix (`VideoId::mix_url`, `RD` + the id; `YtDlp::mix`, capped at `MIX_SIZE` since yt-dlp would page through over a thousand, repeats dropped); logged out, YouTube makes one only for music videos, and for others yt-dlp returns the bare video, which `ytdlp::mix_videos` reports as no Mix. Links (`links.rs`, `links::parse`): a YouTube link typed in the search box (`App::search`) or pasted with no box open (`Event::Paste`, or keystrokes past `PASTED_KEYS`) opens with `App::open_link`. Only YouTube's hosts count (no user, password or port), and only checked ids are kept: `VideoId`, `PlaylistId`, `ChannelId`, `ChannelName` (`@handle`, `/c/`, `/user/`, ASCII only). A video shows as the one card of `View::Link`, as much as the store or the link knows (`App.link`), and nothing is asked of YouTube until it's played; its `t=` is `App.link_start`, used once. A playlist is `View::Playlist` (`YtDlp::playlist`, `PLAYLIST_SIZE`), a handle `YtDlp::named_channel` (the id from the page's `channel_id`), opened when it answers. `WL`/`LL`/`LM` are your account's and open nothing. Resolving a video also reads its details from the same JSON (`Streams.info`), saved and merged before mpv starts, so a link's card fills in.

**Feeds (`feed.rs`).** Each subscription's Atom feed (15 newest uploads; `/shorts/` links mark Shorts), `PARALLEL` at once, `TRIES` tries with backoff (YouTube's feed server fails a lot). A channel's feed is fetched again only when its stored copy is older than `refresh_minutes` (default 30, at least 15, `Settings::refresh_every`), checked every `CHECK_EVERY`; `R` fetches every feed now; Home's header says when feeds were last updated (`App.feeds_updated`). A failed feed waits for the next check (`App.refreshed`). YouTube's feeds go down for everyone now and then (404s for days in Dec 2025, May and Oct 2026): a round whose first `OUTAGE_AFTER` results fail with none loading sets `App.feeds_down` (`FeedsDown::Broken` if YouTube answered, `Unreachable` if nothing did, `feed::answered`), closes the round's semaphore so the rest return `feed::CalledOff` untried, and Home's header says so for as long as it lasts. While down, each round tries only `PROBE` feeds, a different few each time (`App::round_of`); one loading ends it and the rest are fetched at once. While `Broken`, `App::fill_in` looks at the Videos tabs of `FILL_IN_PER_ROUND` channels a round, the most active first (`Store::most_active`), each again once its feed would be due, with yt-dlp's `approximate_date` (`YtDlp::channel(…, dated)`), saved by `Store::save_roughly_dated` so a feed's exact date is never replaced. A feed missing (404) on every try (`feed::NotFound`), in a round where others loaded, gets one background yt-dlp look per session once the round is over (`App::check_gone`, `App.gone_checks`); if yt-dlp says the channel was removed, doesn't exist or was terminated (`app::channel_gone`), it's marked gone (`channels.gone`, `Store::set_gone`): its feed isn't fetched again until you subscribe to it again (x then S or u), and the sidebar dims and marks it for you to unsubscribe (tuitube never unsubscribes for you). Feeds carry no lengths: `App::want_length` (called for each card on screen without one) has yt-dlp list the channel's Videos tab, then its Live tab (`ytdlp::Tab`), 30 videos per look for the cost of one; when each tab was looked at is kept in `channels.videos_checked` / `streams_checked` (`Store::tab_checked`), so a tab is looked at again only for a video newer than that, or every `LIVE_EVERY` for a live stream or premiere on screen. Opening a channel fetches its videos only when the kept ones are older than `refresh_minutes`.

**Store (`store.rs`).** SQLite: `channels` (subscribed flag, photo URL and when it was looked up, when the feed was fetched), `videos` (merged across sources: a later source keeps what an earlier one knew), `watch_later`, `jukebox` (`place` orders it: `e` appends after the largest, `Store::order_jukebox` rewrites them all for `E` and `J`/`K`), `history` (position and length, for resuming and the red watched bar), `playlists` and `playlist_videos` (your playlists, imported from Takeout: `View::MyPlaylist`, under their own rule in the sidebar, `Entry::MyPlaylist`; `x` takes a video off, `C` then `y` deletes one; their videos aren't pruned), `groups` and `group_channels` (your groups of subscriptions, names unique in any case, Unicode's (`Store::group_named`: SQLite's `NOCASE` folds only ASCII), and at most `MAX_GROUP_NAME`: `View::Group`, a feed as Home's of the group's channels you subscribe to, `Store::group_feed`; a channel unsubscribed stays in its groups, uncounted, for if you subscribe again; deleting a group never unsubscribes).

**Channel photos.** `App::avatar_url`: from the store if looked up in the last `AVATAR_EVERY`, else the same background look at the channel's Videos tab as for lengths (`App::look_up_channel`, its own semaphore, so it never delays what you asked for); asked for at 176 px (`ytdlp::small_avatar`).

**What failed.** `App::explain` words a yt-dlp error for the status bar: what YouTube refuses on purpose in tuitube's words (`app::refusal`: a bot check, or a video for signed-in adults, members, Premium or private, with `o` to open it in the browser), else yt-dlp's line, and if `app::youtube_said` doesn't explain it either, a word about updating yt-dlp once it's older than `OLD_AFTER_DAYS` (`ytdlp::old_notice`, the update command guessed from where it's installed; tuitube never updates it). Its version (`YtDlp::version`, `--version` run like any request) is asked for only after such a failure, once a session, and added to the message still shown when it comes; `--check` prints it too.

**Playing.** Enter / `a` → `YtDlp::resolve` (format from `ytdlp::Quality`: at most `max_height` lines, counted across the narrower side as YouTube labels them, so an upright Short's 1080p is 1080×1920 (`aspect_ratio<1` choices first); no AV1 where there's another; the sound from `audio_quality`, `ytdlp::AudioQuality`: `high` is `ba`, `low` is `ba[abr<=80]` then `ba`, since logged out YouTube has only ~130 and ~50–70 kbps) → `Player::start`. The same JSON gives the chapters (`Streams.chapters`; `lenient`, so odd chapters never stop a video playing) and what plays (`Streams.quality`, `1080p60` or `68 kbps`, from yt-dlp's numbers). Picking a quality in the settings (`App::pick_height`, `pick_audio_quality`) plays the video playing again at it from where it is (`App::play_again`, `Resolving.carry_on`), except sound-only for a picture change, while another video loads, in the demo, and on Windows. Audio only (`audio_only`, `App::toggle_audio_only`, `:audio-only`): `App::play` makes every playback sound only (Enter, a description's time, autoplay, `:play`), and turning it on while a picture plays goes on as sound through `play_again`. Sound alone, mpv keeps `player::SOUND_AHEAD` / `SOUND_BEHIND` in memory, not its 150 + 50 MiB, and on macOS starts with `MallocLargeCache=0` (`player::allocator_env`: mpv 0.41 playing sound alone grew from 116 MiB to over 800 MiB in a minute, the allocator caching the large buffers it frees; flat without, same CPU; a picture doesn't grow); with SponsorBlock on, `Settings::skip_categories(listening)` adds `music_offtopic`. Subtitles (`Playing.subtitles`, the track's name): `T` / `:subtitles` / the settings row (`App::toggle_subtitles`); the player bar shows `CC T`, lit while on, only for a video that has a track in your languages. Chapters (`chapters.rs`): `t` opens `App.chapter_menu` (`ChapterMenu`: the chapters, the one playing marked, and a time typed, `chapters::parse_time`: `1:23`, `90`, `+30`, `-1:00`, `50%`); `[` / `]` go to `chapters::previous` (this chapter's start, or the one before within `BACK_WITHIN`, as mpv's `--chapter-seek-threshold`) / `chapters::next`; all through `App::go_to` → `Player::seek_to`, setting `position` at once. mpv gets the chapters on the first `Duration` that holds them all (`Playing.chapters_sent`): it drops the ones past the length it knows. Volume (`volume` in settings, 0–100): mpv starts with it and `mute` (set before the properties are observed, so mpv's first report is tuitube's); `-` / `+` (`VOLUME_STEP`), `:volume`, `m` / `:mute` / `:unmute` (`App.muted`, this session only) go to mpv with `Player::set_volume` / `set_muted`, and mpv's `volume` and `mute` reports (changed in its window too) come back, so the next video plays as loud. Changing the volume unmutes. On macOS mpv starts with `--audio-format=float`: its CoreAudio output doesn't open for 48 kHz planar float (YouTube's Opus and AAC, decoded), and its fallback, AVFoundation, holds 2 s of sound, so a volume change was heard that late (mpv's own `9` / `0` too). It's written to settings.toml on the next tick (`App.volume_unsaved`, `App::save_volume`, and at quit), so a key held down writes once. The player bar shows it after the keys, muted in yellow, only where mpv can be controlled. Resumes from the stored position if it's more than `RESUME_AFTER` from either end (the status bar then says `0` plays it from the start: `App::back_to_start` acts on what plays, never the selection, since `N` doesn't move it: the video loading gets `start_once` at 0 and loses `carry_on`, the one playing `go_to(0.0)`, sound alone staying so; only with nothing playing does it play the selected video, as Enter, from 0); the position is saved every `SAVE_EVERY` and when playback ends. The player bar (`ui::player_bar`) is a box: the title and channel in its border (and "Next: …" on the right of it when autoplay will play it and the title leaves `MIN_NEXT` columns), and inside the position, the chapter it's in (while the bar keeps `MIN_BAR` columns, at most `MAX_CHAPTER_SHOWN`), a bar across with a dot, the length, the quality and the keys with icons (`§ t` for the chapters; `N` only when something is up next; `⟳ A` lit while autoplay is on; `r` lit while repeat is, with its own icon for one), the keys and quality dropped first in a narrow window, then the chapter. Autoplay: playing a card sets `App.up_next` to the cards after it (or, once a Mix of the video playing loads, the rest of the Mix); mpv's `end-file` with reason `eof` (`PlayerEventKind::Ended`) marks the playback ended, and when mpv then exits within `ENDED_WITHIN` of the end with `autoplay` on (`A`), the next one plays, unless a video you chose is still loading. Closing mpv's window or `X` never moves on; a video autoplay can't play is skipped, `MAX_SKIPS` in a row at most, and a bot check stops it. A video that couldn't be played, however it was asked for (`App::could_not_play`: yt-dlp failed, or mpv was refused its stream for good; not another quality of the one playing), is kept in `App.failed` with why, this session, until it's played again: marked ✗ on its card, list row and in up next, selected in the view shown if it's there (N and autoplay don't move the selection otherwise), and while it's selected where Enter plays it (`App::failed_selected`) the status bar says why and that Enter tries again. The Jukebox (`App.jukebox`, kept in the store) plays before `up_next`, and on even with autoplay off (`App::play_next`, `App::plays_next`), from where it is: `App.jukebox_at` (this session only) is the video last picked from it, and `App::jukebox_next` the first playable one after it (from the start while `None`). Videos stay in it as they play; with `jukebox_autoremove` (off by default) one played from it to its end is taken off when mpv exits. Taking off the video it's at (`App::take_off_jukebox`: autoremove or `x`) steps `jukebox_at` back one, so it goes on from the one after. `E` puts a video right after `jukebox_at`. `Resolving`/`Playing.from_jukebox` say a video was picked from it, for `App::jukebox_state` (the ▶ / ⏸ / loading mark in the list and on its card). Playing a card in the Jukebox clears `up_next`: the Jukebox is what follows. `C` clears it after a `y` in a popup (`App.confirm`, `Confirm`: `y` does it, any other key cancels, Enter included, so a paste ending in Enter can't); every removal from a list asks the same way: `x` off the Jukebox, Watch later, History or a playlist, `w` on a video in Watch later (`Confirm::TakeOff`, `app::Kept`, `App::take_off`), and unsubscribing, `S` or `x` in the sidebar (`Confirm::Unsubscribe`). Only autoremove takes a video off unasked. Windows has no mpv events, so no autoplay there (`N` works). The system's ⏭ and ⏮ (media keys, Control Center, notch apps) reach mpv as its `NEXT` and `PREV` keys, bound over the socket before `loadfile` to `script-message tuitube next|previous` (`player::REMOTE_KEYS`); mpv sends those back as a `client-message` (`PlayerEventKind::Remote`, only those two words): ⏭ is `N` (`App::remote_next`), the next chapter when nothing is up next; ⏮ is `[` (`App::remote_previous`), the start in a video without chapters. Not on Windows (no socket). Repeat (`repeat` in settings, `settings::Repeat`; `r` and `:repeat` go round off, all, one as YouTube's loop button, `App::set_repeat`): one is mpv's `loop-file=inf` (`Start.looped` at start, `Player::set_looped` on the video playing, except on Windows), so mpv goes back to the start with no `end-file` between, nothing plays next (`plays_next` is `None`; `N` still plays it), and a jump back to the start from the end (`LAP_FROM_END`, so a seek back from midway isn't one) skips SponsorBlock's segments again (`Skipper::again`), after a lap of at least `MIN_LAP` (`Playing.lap`): a segment over the whole video plays the next lap rather than skipping to the end over and over. A skip sets `position` to where it went. All starts the list the last video was picked from (`App.last_from_jukebox`) again after its last: the Jukebox (`jukebox_next` wraps), or up next's whole list (`App.round`: the view's playable cards or the Mix, put back by `play_next`, with autoplay on as up next is). Shuffle (`shuffle` in settings; `z`, `:shuffle`, the settings tab, `App::toggle_shuffle`; `shuffle.rs`: splitmix64 seeded from `RandomState`, no crate) applies to the Jukebox and to lists `app::shuffles` names (playlists, Watch later, Mixes: `App.round_shuffles`). Each round plays every video once (`once_each`; `Rng::round` never starts one with the video that played last, `App.last_played`). A list's up next is shuffled when it's made (`play_selected`, `on_mix`) or when shuffle turns on (only what's left; off sorts what's left back into `round`'s order); repeat all's next round comes from `App::round_order`. The Jukebox plays in `App.jukebox_order` (`jukebox_queue`): `shuffle_jukebox` makes it (Enter in the Jukebox: that one first; turned on: the rest after where it is), `sync_jukebox_order` keeps it to the Jukebox on every reload (one put in goes somewhere after the one playing, so it plays this round; `E` right after it), and its next round is `jukebox_round`. What plays after a round is shown before it's picked: `up_next_front` and `jukebox_next` work on a copy of `App.rng`, and `play_next` makes the same round with the real one. Resolving has its own counter (`App.resolves`), so starting a video never drops a view's answer. SponsorBlock: once mpv starts, `App::look_up_segments` asks for the video's segments (`AppEvent::Segments`, carrying the playback number); on each `time-pos`, `Skipper::due` returns a segment playback is inside and hasn't skipped yet, run on through the ones that touch it (each left alone if marked on a video whose length differs by more than `LENGTH_SLACK`), and `Player::seek_to` seeks to its end (`absolute+exact`). Each is skipped once, so seeking back into one plays it. The player bar's title row says `[SKIP] <category> · <length>` in the theme's yellow (`warning`) for `SKIP_SHOWN_FOR`, where "Next: …" goes. The seek bar shows the segments over it before they come (`Playing::segments`: the `Skipper`'s that fit the video's length, skipped yet or not), a cell at least each, in `Colors::segment`'s color (`theme::SEGMENT_COLORS`, the palette's nearest to SponsorBlock's extension: sponsors green, self-promotion yellow, intros cyan; never red, which is what played), drawn by `ui::seek_bar`.
**Watch page and Pepper (`ui/watch.rs`, `pepper.rs`).** Enter on a card plays it and opens its watch page (`App.watch`, `Watch`; `p` from anywhere: the video playing, else the selected one; Esc, Backspace, Ctrl-o, `q` or `p` go back, and `show`/`go_back` and `X` (`App::stop`) close it). Laid out as YouTube's: the picture at the top left (`pepper::video_area`, 16:9, leaving `ROWS_UNDER` rows, and at least a third of the height, `UNDER_PART`, so the description and comments have room), the title, channel and views, then Description / Comments as the `i` popup's (`ui::video_info` and `app::info_key`, shared), and up next (`App::up_next_list`: the rest of the Jukebox, then `up_next`) in a column from `UP_NEXT_BESIDE` columns, in the description's place below that. Tab (from up next too) and ← → / `h l` go between Description and Comments; Ctrl with an arrow or `h j k l` goes between them and up next (`WatchPane`), as between the list's panes, and never reaches the panes behind the page; Enter in up next plays that one (`play_up_next`, the ones before skipped). Enter on the page plays its video when that isn't what plays with its picture (`watching_what_plays`). While the page is open, `selected_video` is its video, so `w e E S o y c M a i` and `:` commands act on it, and the cards' own keys don't reach the hidden grid; a new playback with a picture moves the page to it (autoplay, `N`, up next). Outside Pepper the picture is the video's thumbnail, and mpv plays in its window as always. In Pepper (`App.pepper`, set by `main` from `pepper::port()`) with `inline_video` on, `tools.pepper_play` found (`Tools::find_pepper_play`: the `pepper_play` setting or `TT_PEPPER_PLAY`, else `PEPPER_PLAY`, which Pepper gives every shell) and a picture to play, `on_resolved` starts pepper-play instead of mpv (`App::inline_player`; the settings tab says under its row where Pepper comes from), giving it the token before `loadfile` (`Start.pepper`). Each frame `ui::draw` lays out `App.video_box`: the page's picture, or while browsing the picture-in-picture box over the videos' bottom right (`pepper::pip_area`, unless `P` hid it, `App.pip_hidden`), or with `f` (`App.fullscreen`, `App::fills_tab`) the whole tab, drawn black under it, until `f` or Esc (Esc leaves it before it closes the page) or nothing plays or loads; outside Pepper `f` is mpv's `cycle fullscreen`. After the frame, `App::video_placement` writes `OSC 777;pepper;place` where it moved, or `remove` when it's gone (under any popup, when playback stops, when tuitube quits); Pepper tells pepper-play the box's size in pixels itself. pepper-play is Pepper's (`../pepper/pepper-play`, its README the protocol): libmpv, loaded at run time, draws into IOSurfaces Pepper shows; it runs from `Pepper.app/Contents/Helpers/Pepper.app`, so Now Playing and notch apps show it as Pepper, and publishes Now Playing itself (title, the EDL's artist, length, position, pause, and tuitube's cover, the album-art track's file). Not with `now_playing` off (`--input-media-keys=no`). `TT_VIDEO_LOG` (a file) gets what it and mpv say (`PEPPER_PLAY_DEBUG`: from verbose up), to find out why a video stopped; it holds the stream addresses, so it's made 0600 and a link there isn't followed (`player::video_log`).

**Command line (`commands.rs`).** `:` opens `App.command` (`CommandLine`), drawn in place of the status bar (`ui::command_line`) with its completions above it, lined up under the word they complete (`ui::command_menu`). `COMMANDS` is the table: each `Spec` has a name, aliases (`q`, `audio`…), an `Arg` (what it takes, how it completes and reads), whether the argument is optional, what it does and its key; the quick settings come first. `complete` gives the commands matching the first word (name, then aliases, then what it does, then letters in order; `set ` narrows to settings), or once a space follows, the values of its argument (heights, high/low, themes, on/off, places, subscriptions, the chapters, chapter times, the last search, files), the one in use marked and commands that can't run now dimmed. Tab / Shift-Tab, the arrows and Ctrl-n / Ctrl-p put each completion on the line in turn, keeping the list of the line as typed (`CommandLine.typed`). `parse` reads a line into a `Command` (a time alone seeks, as vim's `:42`; `set noX` turns X off), and `App::submit_command` runs it only if the line is whole: only Tab completes, so part of a name runs nothing (`:sp` mustn't turn SponsorBlock on); Enter on a completion Tab put there takes it, and a command waiting for its argument then lists what it takes. Errors show in red on the line, which stays open. `App::run_command` calls the same methods as the keys.

**UI (`ui/`).** Laid out as tuigram's panes: round-bordered boxes (`ui::bordered`), the one with the keys in the accent color (`ui::border`). Arrows and `h j k l` move only in the pane with the keys (`App.focus`: the sidebar, where tuitube starts, or the videos; the search box is the third, `App.prompt` of `PromptKind::Search`); Ctrl with one goes to the pane that way (`app::toward`, `App::go_toward`; from the search box, `on_prompt_key`, keeping what was typed in `App.search_typed`, shown dim and put back by `App::open_search`). In the cards, left and right go past a row's ends to the row before or after. In the sidebar, right opens the row (`App::go_to_videos`): on Search, its results, or the search box while there are none. `mod.rs`: the search box (`search_box`, drawn as the videos' box's title, lined up with the thumbnails), player bar, status bar (key hints written with the keys in backticks, as tuigram's: `hint_spans` shows the keys in the accent color, `hints_fitting` drops whole hints from the end), and the `?` popup (`App.help`, a `HelpMenu`): a Keys tab and a Settings tab (`O` opens it there) of checkboxes (Shorts, live streams, descriptions, every view as a list, autoplay, SponsorBlock, the Jukebox as a list, taking videos off the Jukebox once played, history, Now Playing), choices (video quality, one row per `settings::HEIGHTS`, lit at `Settings::height_choice`; sound quality; the built-in themes; `HelpMenu::is_choice`); Enter saves the row at once (`App::change_setting`). The chapters popup (`ui::chapter_menu`) is drawn the same way, over the rest, and so is the `i` popup (`App.info_popup`, `InfoPopup`, `ui::info_popup`): the selected video's title and numbers, then a Description tab (the stored description, wrapped by `ui::wrap`; the cursor's line lit, Enter on one with a time in it, `app::time_in`, goes there: `App::go_to_in` seeks the video playing or plays it from there through `App.start_once`) and a Comments tab (`App.comments`, `Comments::{Loading, Loaded, Failed}`, `App::load_comments`). `shorts = false` drops Shorts from the sidebar (`App::menu`) and `Settings::hiding` keeps Shorts, live/upcoming videos and blocked ones out of every view but the Jukebox, Watch later, History and your playlists. Blocking is settings.toml only (`Settings::blocks`, read once a reload into `settings::Blocks`): `blocked_channels` entries are a `ChannelId`, a link `links::parse` reads as one, or a name matched in any case (a handle can't be, and is reported at start); `blocked_words` match YouTube's title as whole words in any case (`holds_word`; scripts written without spaces match anywhere), at most `MAX_BLOCKED` of each. The settings tab says how many are blocked, on a line that isn't a row. `list.rs`: the videos as a list, two rows each and a blank one above (`ROWS`), no thumbnails, drawn from the videos' border so each title starts under the view's name and the search box's edge (the Jukebox's numbers there, the selected one's mark in the column before), every view with `list` (for terminals that draw images badly), the Jukebox alone with `jukebox_list` (`App::shows_list`; `v` is `App::switch_layout`: the Jukebox's own setting while `list` is off, else `list`, so the view you're in always turns), one column for `GridShape`, so the grid's keys move a video (a page is the videos that fit whole; the first row of the next shows below). The first row is the title and its marks (Watch later, the Jukebox's place), then the time watched, a line and the length (`line_spans`, as the player bar without its dot, `━` throughout: red as far as you watched, at least a cell once you watched a second, gray after; `0:00` before a video not played; a sixth of the row long, `LINE_MIN`–`LINE_MAX`, from what the title can spare; on every row with a length). The second, under the title, is the channel · views · age as the cards say them (`info_line`: the views left out first, then the age, then the channel cut). The times are as wide as the view's longest length (no line in a view where no video has one), so the lines line up and don't move while scrolling. The line shows only while the title keeps `MIN_TITLE` columns; the title and length always stay. In the Jukebox rows are numbered, and the video playing from it has its mark (`ui::jukebox_mark`) where its number goes. `sidebar.rs`: a box with the logo in its border, the menu (the Jukebox with its count), then each under a rule of its own (`├─ Groups ─┤`) your playlists (if any), your groups (if any, `Entry::Group`, right above what they group) and the subscriptions, scrolled to the selection; `App::reload_subscriptions` keeps the row selected (by its view, `View::same_as`: ids, not names) when rows above it come or go or it's renamed. Groups (`F` from anywhere, `:group`; `App::open_groups`, `GroupMenu`, `ui::group_menu`): a popup for a channel you subscribe to (the sidebar's subscription, else the selected video's, else the channel shown; another channel is told to `S` first) with its groups ticked: `Enter` / `Space` puts it in or takes it out (`App::toggle_in_group`), `n` or "New group" types a name (`Naming`, a paste cleaned into it, `MAX_GROUP_NAME`) and Enter makes the group with the channel in it (`App::name_group`, never with a name in use; with no group yet the popup opens on naming), `r` renames one (not to another's name), `x` deletes one after a `y` (`Confirm::DeleteGroup`, as `C` on a group shown or on its sidebar row; `App::delete_group` and `delete_playlist` drop it from `back` too, `App::forget`). `grid.rs`: a box with the search box in its border (and the feeds' progress on its right when the header doesn't say it), the header, then the cards a column in from the border; `geometry` fits cards of at least `card_width` columns, thumbnails 16:9 in pixels from the terminal's cell size, and the top of the next row in what's left (kitty and block images are cut with `allow_clipping`; sixel/iTerm2 ones show a placeholder there); a card is the thumbnail (with the length badge), then on a shade of its own (the theme's `surface`, `Colors.selected`, a column of padding each side and a blank row closing it) the watched bar, the channel photo (or its initial) beside a two-line title, the channel, views · age, and the description's start. Below 70 columns the sidebar and the grid take turns (the grid while the search box is open).
